The Transport Layer: TCP, UDP, Ports, Reliable Transfer and Congestion

The network layer delivers packets from host to host, on a best-effort basis. Applications, however, are processes, and they usually want more than best effort. This week we study the layer that closes the gap. We look at its services, its two main protocols (UDP and TCP), and how port numbers identify processes. We then see how TCP opens and closes connections, how it delivers data reliably (stop-and-wait and sliding-window transmission), and how it reacts to traffic congestion. Next week (Week 07) looks at the same layer from the programmer's side: sockets and Java client–server programs.

1. Role and services of the transport layer

The network layer (IP) delivers packets from host to host, on a best-effort basis: packets may be lost, duplicated, delayed or delivered out of order. Applications, however, run as processes, and a host typically runs many communicating processes at once: a browser, a mail client, a DNS resolver, an SSH session. The transport layer closes this gap. It provides logical, end-to-end communication between processes running on different hosts.

The transport layer is implemented only in the end systems (hosts), usually inside the operating-system kernel. Routers in the middle of the network process packets only up to the network layer and do not look at transport-layer state. The transport-layer data unit is called a segment in TCP and a datagram in UDP; it is carried as the payload of an IP packet.

Key ideaThe transport layer turns IP's unreliable, host-to-host packet delivery into a service that applications can use directly. UDP adds only the minimum (ports and a checksum). TCP adds a full reliable byte-stream service on top of an unreliable network.

2. Transport protocols

The TCP/IP suite defines several transport protocols. Two of them carry almost all Internet traffic: UDP (User Datagram Protocol; RFC 768, 1980) and TCP (Transmission Control Protocol; originally RFC 793, 1981; consolidated in RFC 9293, 2022). Others exist for specialised needs.

ProtocolTypeMain featuresTypical use
UDPConnectionless, message-oriented8-byte header, no reliability, no ordering, preserves message boundaries, supports broadcast/multicastDNS, DHCP, SNMP, TFTP, NTP, VoIP/video (RTP), online games, QUIC

SCTP (Stream Control Transmission Protocol)Connection-oriented, message-orientedMulti-streaming, multi-homing, reliable messagesTelecom signalling (SIGTRAN), WebRTC data channels

When to choose UDP
  • The application prefers timeliness over reliability (real-time voice and video).
  • Exchanges are a single short request and reply (DNS).
  • Broadcast or multicast is needed.
  • The application wants to implement its own reliability and congestion control (QUIC).
When to choose TCP
  • Every byte must arrive exactly once and in order: web pages, files, e-mail, remote shells.
  • The application prefers the operating system to handle reliability.

3. Port numbers, sockets and multiplexing

A port number is a 16-bit unsigned integer (0–65535) that identifies a communication endpoint inside a host. Combined with an IP address and a transport protocol, it identifies a specific process; more precisely, a specific socket opened by a process.

3.1 Socket address and the 5-tuple

A socket address is the pair (IP address, port), for example 192.168.1.10:51544. A TCP connection is uniquely identified by the 5-tuple (protocol, source IP, source port, destination IP, destination port). Because the tuple includes the client side, a web server can handle thousands of connections on the same local port 443 at the same time: each connection differs at least in the client address or the client port.

3.2 Demultiplexing

  • UDP demultiplexing uses only the destination (IP, port). All datagrams sent to 10.0.0.5:53 go to the same socket, regardless of the sender; the application learns the sender from the received datagram.
  • TCP demultiplexing uses the full 5-tuple. A server has one listening socket (e.g. *:443) plus one connected socket per client; incoming segments are delivered to the connected socket whose 5-tuple matches.
  • Multiplexing is the reverse operation at the sender: data from many sockets is gathered, given transport headers with the correct ports, and passed down to IP.
ExampleA laptop 192.168.1.10 opens two browser tabs to the same server 93.184.215.14:443. The OS assigns two ephemeral ports, e.g. 51544 and 51545. The two connections are (TCP, 192.168.1.10, 51544, 93.184.215.14, 443) and (TCP, 192.168.1.10, 51545, 93.184.215.14, 443). They share the destination socket address but are different connections, so the server's TCP keeps them apart.

4. UDP: User Datagram Protocol

UDP is the simplest possible transport protocol: it adds to IP only port-based multiplexing and an optional error check.

  • Each send operation produces exactly one UDP datagram, and each receive returns exactly one datagram: message boundaries are preserved.
  • There is no connection set-up, no acknowledgment, no retransmission, no ordering and no congestion control.
FieldSizeMeaning
Source port16 bitsPort of the sending process (may be 0 if no reply is expected)
Destination port16 bitsPort of the receiving process
Length16 bitsLength of header + data in bytes (minimum 8); payload max 65,507 bytes over IPv4
Checksum16 bitsOne's-complement sum over a pseudo-header (source/destination IP, protocol 17, UDP length), the UDP header and the data. 0 = not computed (IPv4 only)
Advantages
  • No connection delay.
  • Small header: 8 bytes, vs at least 20 for TCP.
  • No connection state on the server, so it scales to many clients.
  • The application controls exactly what is sent and when.
Disadvantages
  • Losses, duplicates and reordering must be handled by the application if they matter.
  • UDP senders that do not control their rate can harm other traffic.

4.1 Where does 65,507 come from?

The IPv4 Total Length field is 16 bits, so a datagram is at most 65,535 bytes. Subtracting 20 bytes of IP header and 8 bytes of UDP header leaves 65,507 bytes of payload. Such a datagram would be fragmented into about 45 Ethernet-sized fragments, and losing any one of them loses the whole datagram. Practical UDP protocols therefore keep datagrams below the path MTU: DNS used to stay within 512 bytes and EDNS(0) now recommends about 1232, and QUIC uses at least 1200.

5. TCP: Transmission Control Protocol

TCP provides a reliable, ordered, full-duplex byte stream between two processes. The application writes a stream of bytes; TCP splits it into segments, numbers every byte, retransmits what is lost and delivers the bytes in order at the other end. TCP does not preserve message boundaries: two write calls of 5 bytes may arrive as one read of 10 bytes, or as reads of 3 and 7 bytes.

  • Connection-oriented: an explicit handshake creates state at both ends before data flows.
  • Point-to-point and full-duplex: exactly two endpoints; data flows in both directions simultaneously.
  • Reliable: sequence numbers, cumulative acknowledgments, checksums, retransmission timers.
  • Flow control: the receiver advertises the free space in its buffer (the receive window).
  • Congestion control: the sender limits its rate according to the estimated network load (the congestion window).

6. TCP mechanisms

6.1 Connection establishment: the three-way handshake

Before data is exchanged, both ends must agree that a connection exists and must learn each other's Initial Sequence Number (ISN), window size and options. TCP does this with three segments:

  1. SYN: the client (active opener) sends a segment with SYN = 1 and seq = x (its ISN). The client moves to state SYN_SENT.
  2. SYN + ACK: the server (passive opener, in state LISTEN) replies with SYN = 1, ACK = 1, seq = y (its own ISN) and ack = x + 1. The server moves to SYN_RCVD.
  3. ACK: the client acknowledges with ACK = 1, seq = x + 1, ack = y + 1. Both ends are now ESTABLISHED and data may flow.

Why three segments and not two? Each side must have its own ISN acknowledged. With two segments, the server could not be sure that the client received its SYN, and a delayed duplicate SYN from an old connection could open a bogus connection. The SYN and FIN flags each consume one sequence number, which is why the acknowledgments carry x + 1 and y + 1.

Why random ISNs? ISNs are chosen pseudo-randomly (RFC 6528), for two reasons. Segments from an old connection with the same 5-tuple are then unlikely to fall inside the new connection's sequence space, and attackers cannot easily guess sequence numbers to inject data.

6.2 Connection termination and TCP states

Since TCP is full-duplex, each direction is closed independently:

  • The side that closes first sends FIN. The other side acknowledges it, may still send data (a half-closed connection), and later sends its own FIN, which is acknowledged.
  • The side that sent the first FIN waits in TIME_WAIT for 2·MSL (Maximum Segment Lifetime; in practice 30 s to 4 min, 60 s on Linux). This lets a lost final ACK be retransmitted, and lets old duplicates expire.
  • A connection can also be aborted abruptly with RST, for example when a SYN arrives on a port where no process listens.

6.3 Reliable transfer: stop-and-wait transmission

The simplest reliable protocol over an unreliable channel is stop-and-wait ARQ (Automatic Repeat reQuest):

  1. The sender transmits one frame (segment), starts a timer and waits.
  2. The receiver checks the frame and returns an acknowledgment.
  3. If the ACK arrives before the timer expires, the sender transmits the next frame; otherwise it retransmits the same frame.

A 1-bit sequence number (0, 1, 0, 1, …) is enough to let the receiver recognise duplicates caused by lost ACKs.

Stop-and-wait is correct but inefficient on links with a long delay or a high bitrate, because the sender is idle while waiting for each ACK. Let Tt = L / R be the transmission time of a frame (L bits on a link of R bit/s) and RTT the round-trip propagation time. If the ACK transmission time is negligible, the utilisation of the sender is:

U = Tt / (Tt + RTT) = 1 / (1 + 2a), where a = Tprop / Tt     Throughput = U · R

Example: R = 1 Gbit/s, L = 1500 bytes = 12,000 bits, RTT = 30 ms. Then Tt = 12 µs and U = 0.012 / 30.012 ≈ 0.04 %: a 1 Gbit/s link carries only about 400 kbit/s. This motivates pipelining.

6.4 Sliding-window transmission

With sliding-window (pipelined) transmission, the sender may have up to W frames sent but not yet acknowledged.

  • The window covers a range of sequence numbers. When the oldest outstanding frame is acknowledged, the window slides forward and new frames may be sent.
  • Both sender and receiver keep windows: the sender's window says what may be sent, the receiver's window what may be accepted.
U = min(1, W · Tt / (Tt + RTT)). To keep the link fully busy: W ≥ (Tt + RTT) / Tt, i.e. the window must cover the bandwidth-delay product R · RTT.

Model: the sender fills its window, ACKs arrive after the whole window was sent, and a timeout fires when no progress is possible. This is the model used in homework exercise 3.

6.5 Why the sequence-number limits?

With k-bit sequence numbers there are 2k values. In Go-Back-N, if W = 2k and all W ACKs are lost, the receiver cannot tell whether the retransmitted frame 0 is the old frame 0 or the new one, so W ≤ 2k − 1. In Selective Repeat the receiver window also slides, and the old and new windows must not overlap, so W ≤ 2k/2.

6.6 How TCP uses the sliding window

  • TCP numbers bytes, not segments; the window is expressed in bytes.
  • Acknowledgments are cumulative (like GBN), but receivers buffer out-of-order data. The SACK option (RFC 2018) lets them report exactly which blocks arrived, so the sender retransmits only what is missing (like SR).
  • The receiver advertises its free buffer space in the Window field (rwnd); this is flow control. A receiver with a full buffer advertises a zero window, and the sender then sends small window probes until space is available.
  • The 16-bit field limits rwnd to 65,535 bytes. The Window Scale option (RFC 7323) multiplies it by 2S (S ≤ 14), allowing windows up to about 1 GiB on high bandwidth-delay paths.
  • The amount of unacknowledged data the sender may have in flight is min(rwnd, cwnd), where cwnd is the congestion window (§7).

6.7 Retransmission timeout and fast retransmit

TCP measures the round-trip time and adapts its Retransmission Timeout (RTO) using the algorithm of RFC 6298 (α = 1/8, β = 1/4):

first sample R:   SRTT = R;   RTTVAR = R / 2
later samples R:  RTTVAR = (1 - β)·RTTVAR + β·|SRTT - R|
                  SRTT   = (1 - α)·SRTT   + α·R
                  RTO    = SRTT + max(G, 4·RTTVAR)     (G = clock granularity)
on timeout:       RTO = 2·RTO   (exponential back-off)

Waiting for a timeout is slow. If the sender receives three duplicate ACKs for the same byte, it concludes that the following segment was lost (later segments are arriving) and retransmits it immediately: fast retransmit.

7. Traffic congestion and TCP congestion control

7.1 What is congestion?

Congestion occurs when the total rate at which sources send into some part of the network exceeds the capacity of a link or router. Router queues fill up, packets wait longer (increasing delay), and when buffers overflow, packets are dropped. Senders then retransmit, adding even more load. In the extreme, the network carries mostly retransmissions and useful throughput collapses. This congestion collapse was observed on the early Internet in 1986, and led Van Jacobson to design TCP congestion control (1988).

SymptomCauseConsequence
Growing queuing delayArrival rate close to link capacityHigher RTT, poor interactivity, possible premature timeouts
Packet lossBuffer overflow at a routerRetransmissions; wasted capacity on upstream links
Unnecessary retransmissionsDelayed (not lost) packets time outDuplicate copies use bandwidth
Throughput collapseMost capacity used by packets dropped laterThe network delivers little useful data
Flow control vs congestion controlFlow control protects the receiver (rwnd, advertised by the receiver). Congestion control protects the network (cwnd, estimated by the sender). TCP sends at most min(rwnd, cwnd) unacknowledged bytes.

7.2 Approaches

  • End-to-end congestion control. The network gives no explicit feedback; end systems infer congestion from loss and delay. This is classic TCP.
  • Network-assisted congestion control. Routers signal congestion, e.g. with ECN (Explicit Congestion Notification, RFC 3168). A router marks the IP header instead of dropping the packet; the receiver echoes the mark with the TCP ECE flag; the sender reduces cwnd and confirms with CWR.
  • Queue management in routers. Active Queue Management (RED, CoDel, fq_codel) drops or marks packets early to keep queues short.

7.3 TCP congestion-control algorithms (Tahoe / Reno, RFC 5681)

The sender keeps two variables: the congestion window cwnd (in bytes or MSS units) and the slow-start threshold ssthresh. The principle is AIMD (Additive Increase, Multiplicative Decrease): probe gently for more bandwidth while there is no loss, and cut back sharply when loss signals congestion.

7.4 Modern algorithms

  • CUBIC (RFC 9438): cwnd grows as a cubic function of the time since the last loss, which works much better on high bandwidth-delay paths. Default on Linux since kernel 2.6.19, and on Windows since Windows 10 version 1709 / Server 2019.
  • Compound TCP: an older Windows default that combines loss-based and delay-based windows.
  • BBR (Bottleneck Bandwidth and Round-trip propagation time; Google): model-based. It estimates the bottleneck bandwidth and the minimum RTT and paces packets accordingly, instead of reacting only to loss. Available on Linux (tcp_bbr module).
  • QUIC implementations run congestion control in user space, typically CUBIC or BBR.

Fairness. With AIMD, N TCP flows sharing a bottleneck converge towards an equal share R/N each. Applications can bypass fairness by opening many parallel connections, and UDP applications without congestion control are not constrained at all. That is one reason why real-time applications are expected to implement their own rate control.

AIMD fairness: two flows sharing a bottleneck

Each round both flows add 1 MSS. When their sum exceeds the capacity, both halve, as in the classic Chiu–Jain argument. The gap between the flows halves at every loss event, so the shares converge to equal.

8. Summary and key terms

  • The transport layer provides process-to-process communication; it runs only in end systems.
  • Ports (16 bits) plus IP addresses identify sockets; a TCP connection is identified by its 5-tuple.
  • UDP: connectionless, 8-byte header, message-oriented, no reliability; fast and simple.
  • TCP: connection-oriented reliable byte stream, 20–60-byte header, sequence numbers count bytes.
  • The three-way handshake (SYN, SYN-ACK, ACK) synchronises the ISNs; a FIN/ACK exchange closes each direction; TIME_WAIT protects against old duplicates.
  • Stop-and-wait is simple but inefficient (U = Tt/(Tt + RTT)); sliding windows fill the pipe when W ≥ the bandwidth-delay product.
  • Flow control (rwnd) protects the receiver. Congestion control protects the network: cwnd with slow start, congestion avoidance, fast retransmit/recovery and AIMD.

6S → CACK500115010
7S → CACK, PSH50011501500

9C → SFIN, ACK150155010

SYN and FIN each consume one sequence number, while pure ACKs consume none. Segments 6 and 7 are often merged in practice (piggy-backing the ACK on the data). The connection tracer in §6.2 reproduces this table.
Problem 6: Congestion-window trace (TCP Reno)
A TCP Reno sender starts with cwnd = 1 MSS and ssthresh = 16 MSS. Three duplicate ACKs are received at the end of round 9, and a timeout occurs at the end of round 18 (see Figure 6). (a) In which rounds does slow start operate? (b) What are ssthresh and cwnd after each loss event? (c) How many segments are sent in rounds 0–4? (d) What is cwnd in round 22?
Round012345…910…181920212223
cwnd12481617…2110…1812489
Show solution(a) Slow start: rounds 0–4 (cwnd goes from 1 to 16 and reaches ssthresh), and rounds 19–22 after the timeout.
(b) After 3 dup-ACKs at cwnd = 21: ssthresh = ⌊21/2⌋ = 10, cwnd = 10 (fast recovery, then congestion avoidance). After the timeout at cwnd = 18: ssthresh = 9, cwnd = 1.
(c) 1 + 2 + 4 + 8 + 16 = 31 segments.
(d) Round 22: cwnd = 8 (slow start doubling 1, 2, 4, 8). In round 23 doubling would give 16 > ssthresh, so cwnd is capped at 9 and congestion avoidance begins.
Problem 7: Computing the RTO
Using RFC 6298 (α = 1/8, β = 1/4, granularity G negligible), compute SRTT, RTTVAR and RTO after the RTT samples 100 ms and then 140 ms.
Show solutionSample 1 (100 ms): SRTT = 100, RTTVAR = 50, RTO = 100 + 4·50 = 300 ms.
Sample 2 (140 ms): RTTVAR = 0.75·50 + 0.25·|100 − 140| = 37.5 + 10 = 47.5 ms; SRTT = 0.875·100 + 0.125·140 = 105 ms; RTO = 105 + 4·47.5 = 295 ms.
Note: RFC 6298 recommends a lower bound of 1 s for the RTO; Linux uses a minimum of 200 ms. With the 1 s bound, both values would be rounded up to 1 s.
Problem 8: Decoding headers from a hex dump
(a) Decode the UDP header C3 50 00 35 00 2C 1A 2B. (b) Decode the first 16 bytes of a TCP header: D4 31 01 BB 00 00 03 E8 00 00 00 00 A0 02 FA F0.
Show solution(a) Source port 0xC350 = 50000; destination port 0x0035 = 53 (DNS); length 0x002C = 44 bytes, so 36 bytes of payload; checksum 0x1A2B. This is a DNS query from an ephemeral port.
(b) Source port 0xD431 = 54321; destination port 0x01BB = 443 (HTTPS); sequence number 0x000003E8 = 1000; acknowledgment number 0 (not valid yet); data offset 0xA = 10 words = 40 bytes (20 bytes of options); flags 0x02 = SYN; window 0xFAF0 = 64,240 bytes. This is the first segment of a three-way handshake. (Paste both into the header decoder in §5.)

Task W4: Capturing the three-way handshake with Wireshark

  1. Start Wireshark, select the active network interface (Ethernet or Wi-Fi) and start capturing.
  2. Apply the display filter tcp.port == 80 && ip.addr == <server-IP>, or simply http || tcp.flags.syn == 1.
  3. In PowerShell, generate a plain HTTP connection: curl.exe -s -o NUL http://example.com (find the IP with Resolve-DnsName example.com).
  4. Stop the capture. Locate the SYN, SYN-ACK and ACK segments. In the packet details, expand Transmission Control Protocol and note the ports, sequence/ACK numbers, flags, window and options (MSS, SACK_PERM, WS).
  5. Disable relative sequence numbers (Edit → Preferences → Protocols → TCP → Relative sequence numbers) and observe the real ISNs.
  6. Locate the FIN segments that close the connection. Who closed first?
  7. Open Statistics → Flow Graph (select TCP Flows) and save the diagram for your report.

Without Wireshark: the built-in Packet Monitor (administrator). The resulting .pcapng file can be opened later in Wireshark on any machine.

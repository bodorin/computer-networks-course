1. De la serviciile de transport la aplicații

Aplicațiile de rețea sunt formate din procese care schimbă mesaje. Cele două organizări uzuale sunt:

  • Modelul client–server: un proces server rulează permanent la o adresă și un port cunoscute, așteaptă cereri și răspunde la ele. Un proces client pornește comunicarea atunci când are nevoie de un serviciu.
  • Modelul peer-to-peer: fiecare proces este în același timp client și server.

În ambele modele, procesele accesează nivelul transport prin aceeași interfață: socket API (Application Programming Interface), oferită de sistemul de operare.

2. Socket-uri: definiții

DefinițieUn socket este capătul unui canal de comunicare bidirecțional între două procese, creat și gestionat de sistemul de operare. Aplicația îl identifică printr-un handle: un file descriptor pe Linux/Unix, un handle SOCKET pe Windows, un obiect Socket în Java. Rețeaua îl identifică prin adresa de socket (adresă IP, port) și protocolul de transport.
  • Adresa de socket: perechea (adresă IP, port), de ex. 192.168.1.10:5000. În Java: InetSocketAddress.
  • Conexiune: pentru TCP, asocierea a două adrese de socket, identificată prin 5-tuple (protocol, IP local, port local, IP la distanță, port la distanță).
  • Listening socket (socket pasiv): un socket TCP de server care doar acceptă cereri de conexiune; nu transportă niciodată date.
  • Connected socket: un socket TCP legat de o anumită conexiune; el transportă datele. Un server are un listening socket plus câte un connected socket pentru fiecare client.
  • Socket API: setul de apeluri de sistem folosite pentru a crea și utiliza socket-uri. A apărut în 4.2BSD Unix (1983) ca Berkeley sockets, a fost standardizat în POSIX și a fost adoptat pe Windows ca Winsock (Windows Sockets, 1992). Pachetul Java java.net (din JDK 1.0, 1996) învelește același API în clase.
O imagine utilăDacă host-ul este o clădire și adresa IP este adresa ei poștală, porturile sunt cutiile poștale numerotate din hol, iar un socket este ușa anume prin care un proces își trimite și își primește corespondența. Tot ce se află deasupra socket-ului aparține aplicației; tot ce se află sub el (TCP/UDP, IP, driverul) aparține sistemului de operare.

Cine închide primul?Partea care apelează close() prima trimite primul FIN, iar capătul ei de conexiune rămâne apoi în TIME_WAIT. În Figura 1 clientul închide primul, așa că read() din server întoarce null, iar clientul ajunge în TIME_WAIT. În protocolul echo (Listingurile 2–3), clientul trimite BYE, apoi serverul răspunde Goodbye și închide imediat. Clientul citește apoi până când readLine() întoarce null (FIN-ul serverului) și abia atunci închide. Astfel serverul trimite mereu primul FIN, iar capătul lui de conexiune ajunge în TIME_WAIT. Fără această așteptare, cele două apeluri close() ar intra în cursă (race) și oricare parte ar putea ajunge în TIME_WAIT. Pas-cu-pas-ul apelurilor socket de mai jos urmează protocolul echo.

6. Comunicarea client–server TCP în Java

6.1 Pașii

Server TCPClient TCP
1. Creează un ServerSocket pe un port cunoscut (socket + bind + listen).1. Creează un Socket(host, port); acesta execută three-way handshake.
2. Apelează accept(); se blochează până când se conectează un client și întoarce un Socket conectat.2. Obține stream-urile de intrare și de ieșire de la socket.
3. Obține stream-urile de intrare/ieșire de la socket-ul conectat.3. Trimite o cerere și citește răspunsul, conform protocolului de aplicație.
4. Citește cererile, le procesează, scrie răspunsurile.4. Închide socket-ul (trimite FIN).
5. Închide socket-ul conectat; revine la pasul 2 pentru clientul următor.

6.2 Un server TCP echo concurent

Serverul de mai jos ascultă pe un port dat în linia de comandă (implicit 5000). Pentru fiecare client acceptat pornește un thread nou, astfel încât mai mulți clienți pot fi serviți în același timp. Protocolul de aplicație este orientat pe linii:

  • clientul trimite o linie de text;
  • serverul răspunde cu ECHO: urmat de linie cu majuscule;
  • linia BYE încheie sesiunea.

Listingul 2. TcpEchoServer.java

import java.io.*;
import java.net.*;
 
public class TcpEchoServer {
    public static void main(String[] args) throws IOException {
        int port = (args.length > 0) ? Integer.parseInt(args[0]) : 5000;
        try (ServerSocket server = new ServerSocket(port)) {
            System.out.println("Echo server (stream socket) listening on port " + port);
            while (true) {
                Socket client = server.accept();          // se blochează până se conectează un client
                new Thread(() -> handle(client)).start(); // un thread pentru fiecare client
            }
        }
    }
 
    private static void handle(Socket s) {
        String who = s.getInetAddress().getHostAddress() + ":" + s.getPort();
        System.out.println("Connected: " + who);
        try (s;
             BufferedReader in = new BufferedReader(
                     new InputStreamReader(s.getInputStream(), "UTF-8"));
             PrintWriter out = new PrintWriter(
                     new OutputStreamWriter(s.getOutputStream(), "UTF-8"), true)) {
            String line;
            while ((line = in.readLine()) != null) {
                if (line.equalsIgnoreCase("BYE")) { out.println("Goodbye"); break; }
                out.println("ECHO: " + line.toUpperCase());
            }
        } catch (IOException e) {
            System.out.println("Error with " + who + ": " + e.getMessage());
        }
        System.out.println("Disconnected: " + who);
    }
}

Listingul 3. TcpEchoClient.java

import java.io.*;
import java.net.*;
import java.nio.charset.Charset;
 
public class TcpEchoClient {
    public static void main(String[] args) throws IOException {
        String host = (args.length > 0) ? args[0] : "localhost";
        int port = (args.length > 1) ? Integer.parseInt(args[1]) : 5000;
        try (Socket s = new Socket(host, port);   // aici are loc three-way handshake
             BufferedReader in = new BufferedReader(
                     new InputStreamReader(s.getInputStream(), "UTF-8"));
             PrintWriter out = new PrintWriter(
                     new OutputStreamWriter(s.getOutputStream(), "UTF-8"), true);
             BufferedReader kb = new BufferedReader(new InputStreamReader(System.in, keyboardCharset()))) {
            System.out.println("Connected to " + host + ":" + port
                               + " from local port " + s.getLocalPort());
            String line;
            while ((line = kb.readLine()) != null) {
                out.println(line);
                String reply = in.readLine();
                if (reply == null) break;
                System.out.println(reply);
                if (line.equalsIgnoreCase("BYE")) {
                    while (in.readLine() != null) { }   // așteaptă FIN-ul serverului: serverul închide primul
                    break;
                }
            }
        }
    }

    // Tastatura folosește codificarea consolei (adesea o code page veche pe Windows);
    // rețeaua folosește întotdeauna UTF-8.
    static Charset keyboardCharset() {
        Console c = System.console();
        return (c != null) ? c.charset() : Charset.defaultCharset();   // Console.charset(): Java 17+
    }
}

6.3 Explicații

  • new ServerSocket(port) creează listening socket-ul; portul apare ca LISTEN în netstat / ss. Backlog-ul (implicit 50) este lungimea cozii de conexiuni stabilite care așteaptă accept().
  • accept() se blochează; când revine, handshake-ul este deja complet. Socket-ul întors are același port local ca server socket-ul; se deosebește prin adresa și portul clientului.
  • new Socket(host, port) rezolvă numele, alege un port local efemer și execută handshake-ul. Dacă niciun server nu ascultă, aruncă ConnectException.
  • TCP este un byte stream. BufferedReader.readLine() și PrintWriter.println() impun peste el un framing pe linii: fiecare mesaj se termină cu newline.
  • PrintWriter(..., true) activează auto-flush la println(). Fără flush, datele rămân în buffer, iar partenerul așteaptă la nesfârșit: o greșeală clasică.
  • readLine() întoarce null când partenerul închide conexiunea (end of stream, FIN primit). După BYE, clientul folosește acest lucru ca să aștepte până când serverul a închis. Așa se fixează ce parte închide prima (vezi „Cine închide primul?” în §4).
  • try-with-resources închide automat stream-urile și socket-urile, chiar și după o excepție. Specificați întotdeauna UTF-8 pentru stream-urile de rețea, ca mașinile Windows și Linux să poată comunica. Tastatura este o altă poveste: octeții ei vin în codificarea consolei, adesea o code page veche pe Windows. De aceea clientul decodifică System.in cu Console.charset() (Java 17+), iar caracterele cu diacritice sunt trimise corect ca UTF-8.

6.5 Framing-ul mesajelor peste TCP

Deoarece TCP nu păstrează granițele mesajelor, aplicația trebuie să definească unde se termină un mesaj. Există trei tehnici uzuale:

  • un delimitator, de ex. un newline, ca în antetele HTTP, în SMTP și în protocolul nostru echo;
  • un length prefix (prefix de lungime), folosit de protocoalele binare;
  • mesaje de dimensiune fixă.

Un schimb cu prefix de lungime în Java:

Listingul 5. Framing cu length prefix

// emițătorul
DataOutputStream out = new DataOutputStream(new BufferedOutputStream(socket.getOutputStream()));
byte[] msg = text.getBytes(StandardCharsets.UTF_8);
out.writeInt(msg.length);   // lungime pe 4 octeți, big-endian (network byte order)
out.write(msg);
out.flush();
 
// receptorul
DataInputStream in = new DataInputStream(new BufferedInputStream(socket.getInputStream()));
int len = in.readInt();
byte[] buf = new byte[len];
in.readFully(buf);          // repetă până au sosit exact len octeți
String text = new String(buf, StandardCharsets.UTF_8);

7. Comunicarea client–server UDP în Java

7.1 Pașii

Server UDPClient UDP
1. Creează un DatagramSocket(port) pe un port cunoscut.1. Creează un DatagramSocket(); sistemul de operare alege un port efemer.
2. Pregătește un DatagramPacket gol, cu un buffer, și apelează receive(); se blochează până sosește o datagramă.2. Construiește un DatagramPacket cu datele și cu adresa și portul serverului; apelează send().
3. Citește datele (getData(), getLength()) și adresa emițătorului (getAddress(), getPort()).3. Apelează receive() pentru răspuns, cu un timeout (setSoTimeout), deoarece cererea sau răspunsul se pot pierde.
4. Construiește un pachet de răspuns adresat emițătorului și îl trimite cu send(); revine la pasul 2.4. Închide socket-ul.

Listingul 6. UdpEchoServer.java

import java.net.*;
import java.nio.charset.StandardCharsets;
 
public class UdpEchoServer {
    public static void main(String[] args) throws Exception {
        int port = (args.length > 0) ? Integer.parseInt(args[0]) : 6000;
        try (DatagramSocket socket = new DatagramSocket(port)) {
            System.out.println("Echo server (datagram socket) listening on port " + port);
            byte[] buf = new byte[1024];
            while (true) {
                DatagramPacket req = new DatagramPacket(buf, buf.length);
                socket.receive(req);                       // se blochează până sosește o datagramă
                String msg = new String(req.getData(), 0, req.getLength(), StandardCharsets.UTF_8);
                System.out.println("From " + req.getAddress().getHostAddress() + ":"
                                   + req.getPort() + " -> " + msg);
                byte[] ans = ("ECHO: " + msg.toUpperCase()).getBytes(StandardCharsets.UTF_8);
                socket.send(new DatagramPacket(ans, ans.length, req.getAddress(), req.getPort()));
            }
        }
    }
}

    public static void main(String[] args) throws Exception {
        InetAddress server = InetAddress.getByName((args.length > 0) ? args[0] : "localhost");
        int port = (args.length > 1) ? Integer.parseInt(args[1]) : 6000;
        try (DatagramSocket socket = new DatagramSocket();   // port local efemer, fără conexiune
             BufferedReader kb = new BufferedReader(new InputStreamReader(System.in, keyboardCharset()))) {
            int seq = 0;                                     // identificatorul cererii
            String line;
            while ((line = kb.readLine()) != null && !line.equalsIgnoreCase("BYE")) {
                seq++;
                byte[] data = (seq + " " + line).getBytes(StandardCharsets.UTF_8);   // de ex. "3 hello"
                socket.send(new DatagramPacket(data, data.length, server, port));
                String expected = "ECHO: " + seq + " ";      // serverul trimite înapoi identificatorul
                String reply = null;
                long deadline = System.currentTimeMillis() + 2000;   // UDP nu garantează nimic: așteaptă cel mult 2 s
                while (reply == null) {
                    long left = deadline - System.currentTimeMillis();
                    if (left <= 0) break;
                    socket.setSoTimeout((int) left);
                    byte[] buf = new byte[1024];
                    DatagramPacket resp = new DatagramPacket(buf, buf.length);
                    try {
                        socket.receive(resp);
                    } catch (SocketTimeoutException e) {
                        break;
                    }
                    String r = new String(resp.getData(), 0, resp.getLength(), StandardCharsets.UTF_8);
                    if (r.startsWith(expected)) reply = r;   // răspunsul la ACEASTĂ cerere
                    else System.out.println("(ignored a late reply to an earlier request: " + r + ")");
                }
                System.out.println(reply != null ? reply : "No reply within 2 s (datagram or reply lost?)");
            }
        }
    }

    // Tastatura folosește codificarea consolei (adesea o code page veche pe Windows);
    // rețeaua folosește întotdeauna UTF-8.
    static Charset keyboardCharset() {
        Console c = System.console();
        return (c != null) ? c.charset() : Charset.defaultCharset();   // Console.charset(): Java 17+
    }
}

7.2 Explicații

  • Nu există nicio conexiune și niciun accept(): un singur socket de server primește datagrame de la toți clienții, iar răspunsul pleacă la adresa și portul găsite în pachetul primit.
  • Fiecare send() produce exact o datagramă și fiecare receive() întoarce exact una: granițele mesajelor sunt păstrate, deci nu este nevoie de framing.
  • Folosiți întotdeauna getLength(): buffer-ul poate fi mai mare decât datagrama și poate conține încă octeți dintr-un mesaj anterior, mai lung.
  • Dacă buffer-ul este mai mic decât datagrama, octeții în plus sunt aruncați fără nicio avertizare.
  • Payload-ul UDP maxim peste IPv4 este de 65.507 octeți. Datagramele mai mari de aproximativ 1.472 de octeți (MTU Ethernet 1500 − 20 − 8) sunt fragmentate de IP, iar pierderea unui singur fragment pierde întreaga datagramă. Păstrați datagramele mici.
  • Fiabilitatea este treaba aplicației. Clientul își numerotează cererile (3 hello → ECHO: 3 HELLO) și așteaptă cel mult 2 s răspunsul cu numărul potrivit. Fără număr, un răspuns sosit imediat după un timeout ar fi afișat ca răspuns la cererea următoare. Un client robust retransmite și un număr limitat de ori (Tema A2).
  • DatagramSocket.connect(addr, port) nu trimite nimic. Doar fixează partenerul, filtrează datagramele de la alții și permite ca erorile ICMP să apară ca PortUnreachableException.

9. Rezumat și termeni-cheie

  • Un socket este un capăt de comunicare gestionat de sistemul de operare, identificat prin (adresă IP, port, protocol); aplicațiile îl folosesc prin socket API.
  • Socket-urile se clasifică după familia de adrese, tip (stream, datagram, raw, seqpacket), rol, modelul de I/O și modul de livrare.
  • Server TCP: ServerSocket → accept → stream-uri → close. Client TCP: Socket(host, port) → stream-uri → close.
  • Serverul și clientul UDP folosesc amândoi DatagramSocket și DatagramPacket; nu există conexiune, iar aplicația tratează pierderile.
  • TCP are nevoie de framing (delimitatori sau length prefix); UDP păstrează granițele mesajelor.
  • Serverele concurente folosesc thread-uri, thread pool-uri, virtual threads sau selectoare NIO.

10. Seminar: analiză, depanare și proiectarea protocoalelor

Problema 1: Ce apel produce ce pachete?
Pentru programele TCP echo (Listingurile 2 și 3), precizați ce apel Java declanșează fiecare dintre următoarele și în ce thread/proces se întâmplă: (a) segmentul SYN; (b) momentul în care accept() revine; (c) primul segment de date; (d) FIN-ul clientului; (e) un RST în loc de SYN-ACK.
Arată soluția(a) new Socket(host, port) în client (acesta apelează connect()).
(b) Kernel-ul serverului finalizează singur handshake-ul când sosește ultimul ACK; accept() scoate apoi noua conexiune din coadă. Handshake-ul se poate încheia chiar înainte ca accept() să fie apelat.
(c) out.println(line) în client (auto-flush împinge octeții către TCP).
(d) Închiderea socket-ului clientului la sfârșitul blocului try-with-resources (sau shutdownOutput()).
(e) Clientul se conectează la un port pe care nu ascultă niciun server; primește ConnectException: Connection refused.
Parcurgeți pașii cu unealta pas-cu-pas a apelurilor socket din §4.
Problema 2: Numărarea socket-urilor
Serverul TCP echo rulează pe 192.168.1.100:5000. Sunt conectați trei clienți: doi de pe 192.168.1.21 (porturile 50510 și 50511) și unul de pe 192.168.1.35 (portul 61200). (a) Câte socket-uri are deschise procesul server? (b) Scrieți 5-tuple-ul fiecărei conexiuni. (c) Ce arată netstat -an (Windows) sau ss -tan (Linux) pe server pentru portul 5000?
Arată soluția(a) 4 socket-uri: 1 ServerSocket în ascultare + 3 obiecte Socket conectate. Toate au portul local 5000.
(b) (TCP, 192.168.1.100, 5000, 192.168.1.21, 50510); (TCP, 192.168.1.100, 5000, 192.168.1.21, 50511); (TCP, 192.168.1.100, 5000, 192.168.1.35, 61200).
(c) O linie de ascultare și trei linii ESTABLISHED. Cu JVM-ul în mod IPv4 (java -Djava.net.preferIPv4Stack=true TcpEchoServer), netstat -an pe Windows arată TCP 0.0.0.0:5000 0.0.0.0:0 LISTENING și trei linii TCP 192.168.1.100:5000 <client> ESTABLISHED. ss -tan pe Linux arată LISTEN … 0.0.0.0:5000 și trei linii ESTAB. Implicit, Java deschide un singur socket IPv6 dual-stack, așa că listener-ul apare ca [::]:5000 (Windows) sau *:5000 (Linux). Pe Linux conexiunile apar și ele cu adrese IPv4-mapped, de ex. [::ffff:192.168.1.100]:5000. Numărul de socket-uri este același în ambele moduri.

Fiecare fragment de mai jos se compilează, dar nu funcționează corect. Găsiți problema și corectați-o.

    socket.receive(packet);            // după un mesaj de 5 octeți, mesajele următoare sunt tăiate la 5 octeți

Arată soluția(a) Lipsește auto-flush: „HELLO” rămâne în buffer. Folosiți new PrintWriter(socket.getOutputStream(), true) sau apelați out.flush().
(b) print nu trimite newline, așa că readLine() din client nu se încheie niciodată; auto-flush funcționează doar cu println. Folosiți out.println(...).
(c) getData() întoarce tot buffer-ul de 1024 de octeți, inclusiv octeți vechi sau zero. Folosiți new String(packet.getData(), 0, packet.getLength(), UTF_8).
(d) receive() setează lungimea pachetului la dimensiunea datagramei primite, iar următorul receive() poate stoca cel mult atâția octeți. Apelați packet.setLength(buf.length) înainte de fiecare receive() sau creați un pachet nou în buclă.
(e) Server iterativ: un client îi blochează pe ceilalți. Serviți fiecare client într-un thread separat sau într-un thread pool (comparați cu simulatorul de concurență din §6.4).

Discuție: de ce un emițător UDP nu află de pierderea datagramei sale, în timp ce un emițător TCP știe întotdeauna (în cele din urmă) dacă datele lui au ajuns?
DiscuțieUDP nu are confirmări (acknowledgments) și nici stare de conexiune; kernel-ul predă datagrama nivelului IP și o uită, așa că pierderea trece neobservată. Singurul feedback este, ocazional, o eroare ICMP, vizibilă doar socket-urilor conectate. TCP păstrează fiecare octet neconfirmat, așteaptă timeout-ul și retransmite. Dacă partenerul nu confirmă niciodată, conexiunea eșuează în cele din urmă cu o eroare (timeout sau reset), deci emițătorul află mereu rezultatul. Aplicația poate totuși pierde date pe care TCP le-a livrat în buffer-ul partenerului înainte ca aplicația acestuia să cadă; de aceea există confirmări la nivelul aplicației.
Problema 5: Proiectarea unui protocol de aplicație
Proiectați un protocol text pentru un serviciu de calculator peste TCP. Clientul trimite operații cu două numere; serverul întoarce rezultatul sau o eroare. Apoi adaptați proiectul pentru UDP.
O soluție posibilă
  • Cereri (câte o linie, terminată cu \n): ADD a b, SUB a b, MUL a b, DIV a b, QUIT.
  • Răspunsuri (o linie): OK <result> sau ERR <message>, de ex. ERR division by zero, ERR unknown operation POW, ERR operands must be numbers.
  • Sesiunea: după conectare, clientul poate trimite oricâte cereri. La QUIT se răspunde cu OK bye, iar serverul închide conexiunea.
  • Versiunea UDP: fiecare cerere trebuie să fie de sine stătătoare și să poarte un identificator, de ex. 17 ADD 3 4 → 17 OK 7. Clientul retransmite după un timeout (de cel mult 3 ori) și ignoră răspunsurile al căror identificator nu se potrivește. Deoarece ADD/SUB/MUL/DIV sunt idempotente, execuția dublă cauzată de retransmisie este inofensivă.

Problema 6: Framing
Un client TCP execută out.write("HELLO".getBytes()); out.write("WORLD".getBytes());. Serverul execută o singură dată int n = in.read(buf);. Enumerați valorile posibile ale lui n și conținutul lui buf. De ce rezultatul nu este determinist? Propuneți două moduri prin care serverul să primească exact cele două cuvinte.
Arată soluțian poate avea orice valoare de la 1 la 10: „HELLOWORLD” într-o singură citire, sau „HELLO”, sau „HEL” și așa mai departe. TCP livrează un stream. Granițele segmentelor depind de algoritmul lui Nagle, de dimensiunea buffer-elor, de MSS și de temporizare, iar read() din receptor întoarce ce este disponibil.
Soluții: (1) un delimitator: trimiteți HELLO\nWORLD\n și citiți cu readLine(); (2) un length prefix: writeInt(5) + octeții, citiți cu readInt() + readFully() (Listingul 5). Simulatorul de framing din §6.5 arată toate cele trei moduri de citire pe același stream.

Exerciții propuse (temă)

  1. Rescrieți serverul TCP echo astfel încât să fie iterativ. Rulați doi clienți și descrieți ce se întâmplă.
  2. Modificați clientul TCP echo pentru a seta un connect timeout de 3 s și un read timeout de 5 s. Testați-l cu o adresă inaccesibilă.
  3. Scrieți un client UDP care trimite cât de repede poate 100 de datagrame numerotate și un server care le numără și raportează numerele lipsă. Rulați-l între două mașini prin Wi-Fi.
  4. Explicați de ce un server HTTP/1.1 trebuie să cunoască lungimea fiecărui corp de răspuns (Content-Length sau chunked encoding).
  5. Comparați numărul de pachete necesare pentru un schimb cerere–răspuns cu TCP (inclusiv stabilirea și eliberarea conexiunii) și cu UDP.
Indicii pentru temă 1. Al doilea client se conectează imediat (kernel-ul finalizează handshake-ul și pune conexiunea în backlog), dar nu primește niciun răspuns până când primul client trimite BYE.
2. Socket s = new Socket(); s.connect(new InetSocketAddress(host, port), 3000); s.setSoTimeout(5000); Prindeți SocketTimeoutException în ambele locuri.
4. HTTP/1.1 păstrează conexiunea deschisă pentru mai multe cereri (persistent connections), așa că sfârșitul corpului nu poate fi semnalat prin închiderea conexiunii: este framing prin length prefix sau prin chunks.
5. Un singur schimb cerere–răspuns peste TCP: 3 (handshake) + 2 (cerere, răspuns; ACK-uri piggy-backed sau întârziate, plus 1 dacă răspunsul este confirmat separat) + 4 (sau 3) pentru închidere ≈ 9 segmente. UDP: 2 datagrame. Unealta pas-cu-pas din §4 numără aproximativ 13, deoarece sesiunea echo are două schimburi (o linie, apoi BYE).

Sarcina L7: Erori tipice, inclusiv porturile privilegiate

  • Reproduceți cele patru erori din Sarcina W7.
  • Rulați java TcpEchoServer 80 ca utilizator obișnuit → BindException: Permission denied. Pe Linux, porturile sub net.ipv4.ip_unprivileged_port_start (implicit 1024) sunt rezervate pentru root; Windows nu are această restricție. Nu rulați serverul ca root; folosiți un port ≥ 1024.
  • Porniți serverul, conectați un client, încheiați sesiunea cu BYE, opriți serverul cu Ctrl+C și reporniți-l imediat. Rulați ss -tan state time-wait '( sport = :5000 )': conexiunea veche este încă în TIME_WAIT pe partea serverului (serverul a închis primul), totuși repornirea reușește. Motivul este că OpenJDK activează SO_REUSEADDR pe orice ServerSocket pe Linux. Ca să vedeți eroarea pe care această opțiune o previne, repetați experimentul. După oprirea serverului, rulați programul mic de mai jos în loc să reporniți serverul. El dezactivează opțiunea înainte de bind, așa că eșuează cu BindException: Address already in use cât timp există intrarea TIME_WAIT (aproximativ 60 s pe Linux). Explicați rolul lui setReuseAddress(true). 
    import java.net.*;

public class ReuseOff {
    public static void main(String[] args) throws Exception {
        int port = (args.length > 0) ? Integer.parseInt(args[0]) : 5000;
        try (ServerSocket s = new ServerSocket()) {      // încă nelegat
            s.setReuseAddress(false);                     // valoarea implicită în OpenJDK pe Linux este true
            s.bind(new InetSocketAddress(port));
            System.out.println("Bound to port " + port + " with SO_REUSEADDR off");
        }
    }
}
    java ReuseOff.java 5000      # în cel mult 60 s de la închiderea sesiunii: BindException
java TcpEchoServer 5000      # reușește: SO_REUSEADDR este activ implicit

12. Anexă: soluția de referință pentru A1 (pentru cadrul didactic)

Un server de tip calculator concurent, care folosește un thread pool. Poate fi testat cu clientul TCP echo din Listingul 3 (java TcpEchoClient localhost 5001), cu ncat / nc sau, într-o simulare în browser, cu testerul de protocol din Problema 5 a seminarului.

Listingul 8. CalcServer.java

import java.io.*;
import java.net.*;
import java.util.concurrent.*;
 
/** Protocol: cerere "OP a b\n" cu OP din {ADD,SUB,MUL,DIV};
 *  răspuns "OK result\n" sau "ERR message\n". */
public class CalcServer {
    public static void main(String[] args) throws IOException {
        int port = (args.length > 0) ? Integer.parseInt(args[0]) : 5001;
        ExecutorService pool = Executors.newFixedThreadPool(20);
        try (ServerSocket server = new ServerSocket(port)) {
            System.out.println("Calculator server on port " + port);
            while (true) {
                Socket c = server.accept();
                pool.submit(() -> serve(c));
            }
        }
    }
 
    static void serve(Socket c) {
        try (c;
             BufferedReader in = new BufferedReader(
                     new InputStreamReader(c.getInputStream(), "UTF-8"));
             PrintWriter out = new PrintWriter(
                     new OutputStreamWriter(c.getOutputStream(), "UTF-8"), true)) {
            String line;
            while ((line = in.readLine()) != null) {
                if (line.trim().equalsIgnoreCase("QUIT")) { out.println("OK bye"); break; }
                out.println(compute(line.trim()));
            }
        } catch (IOException e) { /* clientul a dispărut */ }
    }
 
    static String compute(String req) {
        String[] p = req.split("\\s+");
        if (p.length != 3) return "ERR usage: OP a b";
        try {
            double a = Double.parseDouble(p[1]), b = Double.parseDouble(p[2]);
            switch (p[0].toUpperCase()) {
                case "ADD": return "OK " + (a + b);
                case "SUB": return "OK " + (a - b);
                case "MUL": return "OK " + (a * b);
                case "DIV": return (b == 0) ? "ERR division by zero" : "OK " + (a / b);
                default:    return "ERR unknown operation " + p[0];
            }
        } catch (NumberFormatException e) {
            return "ERR operands must be numbers";
        }
    }
}

Exemplu de sesiune (verificat):

ADD 3 4        ->  OK 7.0
DIV 1 0        ->  ERR division by zero
POW 2 3        ->  ERR unknown operation POW
MUL 2.5 4      ->  OK 10.0
QUIT           ->  OK bye

2. State on top of a stateless protocol: cookies

HTTP is stateless: each request is understood on its own, and the server need not remember the previous one. Yet many applications need state: a login, a shopping basket, a language preference. The Web's answer, standardised in RFC 6265, is the cookie: a small piece of data the server asks the browser to store and to send back with later requests.

  1. The first response carries a header such as Set-Cookie: session=7f3a9c; Path=/; HttpOnly; Secure; SameSite=Lax.
  2. The browser stores the cookie, together with the site it came from.
  3. Every later request to that site carries it back: Cookie: session=7f3a9c.
  4. The server uses the value as a key into its own database, where the actual state lives: who you are, what is in your basket.

So there are four ingredients:

  • a header line in the response (Set-Cookie);
  • a header line in the request (Cookie);
  • a file kept by the browser;
  • a database kept by the server.

The protocol itself stays stateless. The state lives at the two ends, connected by the cookie value: another instance of the end-to-end argument of Lecture 2.

2.1 Cookies and privacy

A cookie set by the site you visit is a first-party cookie. A page may also load objects from a third party, such as an advertisement, a "like" button or an analytics script, whose response can set its own third-party cookie. The same third party is embedded in thousands of sites, so its cookie lets it follow one browser across all of them and build a profile of the user.

This is why European law (the ePrivacy Directive and the GDPR) requires consent for non-essential cookies. It is also why browsers increasingly restrict third-party cookies: Safari and Firefox block them by default.

3. Web caching, the conditional GET and content distribution

A web cache keeps copies of recently requested objects, so that later requests can be served without going back to the origin server. Caches exist at several places:

  • inside the browser;
  • in a proxy run by an institution or ISP;
  • in reverse proxies in front of a server;
  • in the servers of a content distribution network (CDN).

A shared proxy is both client and server. It receives the browser's request and answers from its store if it can. Otherwise it forwards the request to the origin, keeps a copy of the response and passes it on.

Caching helps in three ways:

  • the response time falls for objects found in the cache (a hit);
  • the traffic on the access link falls, which may postpone an expensive upgrade;
  • the origin server carries less load.
Worked example: what a cache does to an access link

An institution's network (1 Gbit/s) reaches the Internet through a 100 Mbit/s access link. Users request 95 objects per second; objects average 1 Mbit; an origin server is on average 1 s away (round trip and server time).

  • Without a cache. The access-link traffic intensity is ρ = 95 × 1 / 100 = 0.95. With the M/M/1 formula of Lecture 2, the average delay on the link is (L/R) / (1 − ρ) = 10 ms / 0.05 = 200 ms. A request takes about 1.2 s, and five per cent more traffic would make it explode.
  • With a cache (hit rate 40 %). Only 57 objects per second cross the link: ρ = 0.57, and the link delay is 10 / 0.43 ≈ 23 ms. The average response time is ≈ 0.4 × (a few ms on the LAN) + 0.6 × (1 s + 0.023 s) ≈ 0.62 s.

The cache halves the response time without buying a faster link.

3.1 Freshness and validation

A cache must not serve a stale copy. HTTP caching (RFC 9111) gives it two tools:

  • Freshness. The server says how long the copy may be used without asking, with Cache-Control: max-age=3600 (seconds) or the older Expires date. A cache reports how long it has held a copy in the Age header.
  • Validation. When a copy is no longer fresh, the cache asks the origin whether it has changed, with a conditional GET.
GET /files/notes.pdf HTTP/1.1                    HTTP/1.1 304 Not Modified
Host: cn.example.edu                             ETag: "5f3a-1e2b4"
If-None-Match: "5f3a-1e2b4"                     Cache-Control: max-age=3600
If-Modified-Since: Fri, 16 Oct 2026 14:12:30 GMT

The validators are the ETag, an opaque version identifier that the server attached to the object, and the Last-Modified date.

  • If the object has not changed, the server answers 304 Not Modified without a body. The cache refreshes its copy's lifetime and serves it.
  • If it has changed, the server answers 200 with the new object.

A small request and a small response replace a full transfer. This is the conditional GET you met in Seminar 3, Problem 4.

4. HTTP/2 and HTTP/3

HTTP/1.1 sends one message after another on a connection. A large or slow response delays everything queued behind it: head-of-line blocking. Browsers work around it by opening six parallel connections per server, each with its own handshake and its own slow start.

HTTP/2 (2015, now RFC 9113) and HTTP/3 (2022, RFC 9114) keep HTTP's semantics: methods, status codes, headers, URLs. They change only how messages are carried.

4.1 HTTP/2: one connection, many streams

  • Binary framing. Messages are cut into frames, each with a 9-byte header giving its length, type and stream identifier. HEADERS frames carry the header fields, DATA frames the body.
  • Multiplexing. Each request–response exchange is a stream, and frames of many streams are interleaved on one TCP connection. A large image no longer holds back a small script: the sender interleaves their frames, and can give priorities.
  • Header compression (HPACK). Header fields such as cookies and the user agent repeat from request to request. HPACK sends an index into a table of previously sent fields instead of the text.
  • Server push let a server send objects before they were requested. It proved hard to use well, and the major browsers now disable it.

HTTP/2 removes head-of-line blocking at the HTTP level, but not at the TCP level. TCP delivers a byte stream in order, so a single lost segment stops all streams until it is retransmitted. On lossy mobile and Wi-Fi links, one HTTP/2 connection can be slower than six HTTP/1.1 connections.

4.2 HTTP/3: HTTP over QUIC

QUIC (RFC 9000, 2021) is a transport protocol built on UDP and implemented inside applications.

  • It provides reliable, congestion-controlled independent streams: a loss stops only the stream it belongs to.
  • It integrates TLS 1.3. A new connection needs a single round trip before the request, and a resumed one can send its request at once (0-RTT).
  • QUIC connections are identified by connection IDs rather than by the 4-tuple. A phone moving from Wi-Fi to the mobile network therefore keeps its connection.

HTTP/3 is HTTP over QUIC, with QPACK in place of HPACK. A browser learns that a server supports it from an Alt-Svc response header or from a DNS record. Today a large share of web traffic, in particular to Google, Meta and Cloudflare, uses HTTP/3.

5. HTTPS: HTTP over TLS

HTTPS is HTTP sent through TLS (Transport Layer Security, version 1.3 in RFC 8446) on port 443. TLS sits between the application and TCP: the application writes plain bytes into a TLS library, which encrypts them and writes records to the socket. It provides three guarantees:

  • confidentiality: an observer cannot read the data;
  • integrity: any change to the data in transit is detected;
  • server authentication: the client knows it talks to the owner of the name it asked for, not to an impostor. Client authentication is optional.

5.1 The handshake

Before data flows, client and server agree on algorithms and keys. In TLS 1.3 the exchange runs as follows:

  1. The client's first message (ClientHello) already carries its supported cipher suites and a key share: its half of an elliptic-curve Diffie–Hellman exchange.
  2. The server answers with its own key share (ServerHello), its certificate, a signature proving that it holds the certificate's private key, and a Finished message. From that moment both sides compute the same session keys, which no observer can compute.
  3. The client checks the certificate and sends its own Finished. In the same flight it sends its first HTTP request.

TLS 1.2 needed one more round trip. QUIC combines the transport and TLS handshakes.

5.2 Certificates and the chain of trust

Encryption alone is not enough: a man in the middle could run a handshake with each side and relay the data. The server therefore presents an X.509 certificate binding its name (for example www.example.org) to its public key, signed by a certification authority (CA). The browser checks three things:

  • that the name matches;
  • that the dates are valid;
  • that the signature chain leads, through one or more intermediate certificates, to a root certificate in the trust store shipped with the operating system or browser.

Certificates are cheap and automated today: Let's Encrypt issues free ones through the ACME protocol. Every certificate issued is also logged publicly (Certificate Transparency), so a CA cannot secretly issue one for your name.

6. Remote login in clear: TELNET

Using a computer from far away was one of the first network applications. TELNET (RFC 854, 1983; port 23) gives a user at one host an interactive terminal session on another, over TCP. It defines a network virtual terminal (NVT): a standard, line-oriented terminal with 7-bit ASCII and CR LF line endings, so that neither side needs to know the other's real terminal.

TELNET's fatal weakness is that everything travels in clear, including the user name and password. Anyone who can capture packets on the path, on a shared Wi-Fi or in a compromised router, reads them, and can even inject commands into the session. You will see this with your own eyes in the laboratory.

TELNET survives today only on old network equipment and embedded devices, and that survival has a price. In 2016 the Mirai botnet took over hundreds of thousands of cameras and routers simply by trying factory passwords on their TELNET ports. The telnet program remains useful in another role: as a tool for typing text protocols by hand, as you did with nc in Lab 1.

6.1 Option negotiation

Features beyond the NVT are agreed through option negotiation, carried in the data stream and introduced by the byte IAC (interpret as command, 255). Either side may offer or request an option with a three-byte command; the other side agrees or refuses.

7. SSH: secure shell, secure tunnels

SSH (Secure Shell; Tatu Ylönen, 1995; SSH-2 standardised in RFCs 4251–4254, 2006; port 22) replaced TELNET and the BSD r-commands (rlogin, rsh, rcp). It offers remote login, remote command execution and file transfer, all over one encrypted and authenticated TCP connection. OpenSSH, developed by the OpenBSD project, is the implementation on almost every Linux and macOS system and, since 2018, a built-in part of Windows.

7.2 Host keys: is this really the server?

Each SSH server has a long-term host key pair. During the key exchange the server signs the exchange with its private host key, and the client verifies the signature with the public host key. But how does the client know that this public key belongs to the real server? There is usually no certificate authority.

  • On the first connection, OpenSSH shows the key's fingerprint (for example SHA256:3j8f…) and asks the user to confirm it.
  • The key is then stored in ~/.ssh/known_hosts, and every later connection must present the same key.

This model is called trust on first use (TOFU). If the key ever changes, the client refuses to connect, with the warning "REMOTE HOST IDENTIFICATION HAS CHANGED!". Either the server was reinstalled, or someone is in the middle. An administrator can publish fingerprints in advance, or in DNS (SSHFP records).

7.3 Public-key user authentication

Passwords can be guessed, phished or captured by a compromised server. With public-key authentication:

  • The user generates a key pair (ssh-keygen -t ed25519).
  • The public key is installed on the server in ~/.ssh/authorized_keys.
  • The private key stays on the laptop, protected by a passphrase.

To log in, the client signs a value that depends on the current session with the private key, and the server checks the signature with the stored public key. The private key never leaves the laptop, and the signature is useless in any other session. Public-key authentication is the norm for administrators and for automated tools such as Git.

8. FTP: two connections and a stateful dialogue

FTP (File Transfer Protocol; RFC 959, 1985, by J. Postel and J. Reynolds, building on work since 1971) is one of the oldest Internet applications still in use. A user logs in to a remote host and lists, downloads, uploads, renames and deletes files. Three features set it apart from HTTP:

  • it uses two kinds of TCP connection;
  • it is stateful;
  • it says precisely how the data being transferred are organised.

8.1 Connection management: control and data

The client opens a control connection to port 21 of the server and keeps it for the whole session. Commands and replies travel on it as lines of NVT-ASCII text, exactly as in TELNET. For every file and every directory listing, a separate data connection is opened, used for that one transfer, and closed. FTP therefore sends its control information out of band, on a connection separate from the data, whereas HTTP sends headers and body in band on one connection.

  • Active mode (the original). The client listens on a port and announces it with PORT h1,h2,h3,h4,p1,p2: the client's IP address as four decimal bytes and the port as two, with port = p1 × 256 + p2. The server then connects to the client, from its port 20.
  • Passive mode. The client sends PASV. The server opens a listening port and announces it in the reply 227 Entering Passive Mode (h1,h2,h3,h4,p1,p2), and the client connects to the server. Both connections are opened by the client.
  • Extended versions for IPv6 (RFC 2428): EPRT |2|2001:db8::5|51001| and EPSV, answered 229 Entering Extended Passive Mode (|||50123|).

Why a new data connection for every file? In the default transfer mode, the end of the file is marked by closing the data connection: the simplest possible answer to the framing problem of Lecture 3.

The same design explains FTP's difficulty with firewalls and NAT. The data connection is opened towards an address and a port written inside a control message.

  • A client behind a home router announces its private address in PORT, and the server's connection attempt cannot reach it. Passive mode solves the client side.
  • A server behind NAT must announce its public address and a fixed range of passive ports.
  • Many routers contain an FTP application-level gateway that reads and rewrites PORT commands: a layering violation we return to with NAT next week.

8.4 State, security and FTP today

An FTP server keeps per-session state:

  • whether the user has logged in;
  • the current directory;
  • the TYPE, MODE and STRU in force;
  • a pending RNFR.

HTTP keeps none, which is one reason HTTP scales to millions of clients more easily.

Like TELNET, plain FTP sends the password in clear on the control connection. Three secure alternatives exist:

  • FTPS: FTP over TLS, either upgraded with the command AUTH TLS (RFC 4217) or on its own port 990;
  • SFTP and scp over SSH;
  • for most downloads, simply HTTPS.

The major browsers removed FTP support in 2021. FTP survives in scientific and public archives (often anonymous), in web hosting, and in industrial and legacy systems. That is why every network engineer must still be able to read an FTP dialogue.

9. Summary and key terms

  • HTTP stays stateless; cookies connect a browser to state kept by the server. Third-party cookies enable tracking across sites.
  • Caches (browser, proxy, CDN) cut response time and link load. Two tools keep copies correct:
    • freshness, with Cache-Control: max-age;
    • validation, with a conditional GET (ETag / If-None-Match), answered 304.
  • HTTP/2 multiplexes binary frames of many streams over one TCP connection and compresses headers; TCP-level head-of-line blocking remains. HTTP/3 runs over QUIC: independent streams over UDP, TLS 1.3 built in, 1-RTT and 0-RTT setup, connection migration.
  • HTTPS = HTTP over TLS: confidentiality, integrity, and server authentication through certificates and a chain of trust. TLS 1.3 needs one round trip. The server name (SNI), the addresses and the sizes remain visible.
  • TELNET gives a network virtual terminal and negotiates options with IAC sequences, but sends everything, passwords included, in clear.
  • SSH has three layers:
    • transport: key exchange, host-key server authentication, encryption;
    • user authentication: password or public key;
    • connection: channels.
    Host keys are trusted on first use. Channels carry shells, commands, scp/SFTP and port forwarding.
  • FTP uses a persistent control connection (port 21) and a data connection per transfer. The data connection is opened by the server in active mode (PORT) or by the client in passive mode (PASV). Replies have three-digit codes. TYPE, STRU and MODE define how data are represented, structured and transmitted. FTP is stateful and sends passwords in clear; FTPS and SFTP are the secure alternatives.

10. Review questions and exercises

The source gives answers for the exercises. For the review questions a short model answer has been added; try to answer before opening it.

R1. HTTP is stateless, yet a shop remembers your basket. Where exactly is the basket stored, and what travels in each request?
Model answerThe basket is stored in the server's database, keyed by a session identifier. Each request carries only that identifier, in the Cookie header that the browser sends back after receiving it in Set-Cookie.
R2. Why does HttpOnly protect a session cookie against a script injected into the page? What does Secure protect against?
Model answerHttpOnly hides the cookie from JavaScript (document.cookie), so an injected script cannot read and steal it, although the browser still sends it with requests. Secure makes the browser send the cookie only over HTTPS, so an observer on the path never sees it in clear.
R3. A cache holds a copy whose max-age has expired. Must it download the object again? Explain the alternative.
Model answerNo. It sends a conditional GET with If-None-Match (the ETag) or If-Modified-Since. If the object is unchanged, the server answers 304 Not Modified with no body, and the copy becomes fresh again.
R4. Which header does a server use to tell a cache that a page may be stored but must be checked before every use?
Model answerCache-Control: no-cache. (Not no-store, which forbids storing at all.)
R5. HTTP/2 multiplexes streams on one connection. Why can one lost packet still delay all of them, and how does HTTP/3 avoid this?
Model answerAll streams share one TCP byte stream, which is delivered strictly in order, so bytes after the lost segment wait for its retransmission whatever stream they belong to. QUIC delivers each stream independently, so a loss delays only its own stream.
R6. List what an observer on the path learns about an HTTPS visit, and what remains hidden.
Model answerVisible: IP addresses, ports, the server name (SNI and the DNS query), and the timing, sizes and number of records and connections. Hidden: method, path, query, all headers including cookies, and the bodies.
R7. What would go wrong if TLS encrypted the data but the server presented no certificate?
Model answerThe client could not tell the real server from a man in the middle. The attacker would run one encrypted session with the client and another with the server, reading and changing everything in between.
R8. What does SSH show on the first connection to a new server, and what does the warning "REMOTE HOST IDENTIFICATION HAS CHANGED" mean?
Model answerOn the first connection, SSH shows the fingerprint of the server's host key and asks for confirmation; the key is then stored in known_hosts. The warning means the server now presents a different key: either it was reinstalled, or someone is in the middle.
R9. With public-key authentication, what does the server store, what does the client keep, and what is sent during login?
Model answerThe server stores the public key (authorized_keys). The client keeps the private key, protected by a passphrase. During login, the client sends a signature over session-specific data, never the key itself.
R10. Why does active-mode FTP fail for a client behind a home NAT router, while passive mode works?
Model answerIn active mode the client announces its private address in PORT, and the server must connect inward. That address is unreachable, and the NAT has no mapping for an unsolicited incoming connection. In passive mode the client opens both connections outward, which NAT handles.
R11. Why must a PNG image be transferred with TYPE I rather than TYPE A?
Model answerTYPE A converts line endings: every 0x0A may become 0x0D 0x0A, or CR LF pairs may become LF. A PNG contains such bytes as data (its signature itself contains 0D 0A and 0A), so the file would be corrupted. TYPE I transfers bytes unchanged.
R12. In FTP's stream mode, how does the receiver know where a file ends? Compare with HTTP/1.1.
Model answerThe sender closes the data connection at the end of the file. HTTP/1.1 keeps the connection open and marks the end of the body with Content-Length or chunked encoding, which allows reuse of the connection.

Problem 1

B. Caches and freshness

Problem 2
A faculty network reaches the Internet through a 200 Mbit/s link. Users request 160 objects per second of 1 Mbit on average, and the origin servers are on average 0.6 s away (round trip plus server time). Use d = (L/R) / (1 − ρ) for the access link and ignore delays inside the faculty.
  1. Compute the traffic intensity of the access link and the average response time.
  2. Option 1: upgrade the link to 1 Gbit/s. Compute the new response time.
  3. Option 2: a proxy cache with a hit rate of 35 %; a hit is answered in 4 ms. Compute the new response time.
  4. Which option would you recommend, and what else does the cache save?
Show solution 1. ρ = 160 × 1 / 200 = 0.8; L/R = 5 ms; d = 5 / 0.2 = 25 ms. Response ≈ 0.6 + 0.025 = 0.625 s.
2. ρ = 0.16; L/R = 1 ms; d = 1 / 0.84 ≈ 1.2 ms. Response ≈ 0.601 s: almost no gain, because the 0.6 s of the Internet path dominates.
3. 104 objects/s cross the link: ρ = 0.52, d = 5 / 0.48 ≈ 10.4 ms. Response = 0.35 × 0.004 + 0.65 × (0.6 + 0.0104) ≈ 0.40 s.
4. The cache. It is cheaper and cuts the response time by a third, because a hit avoids the distant server altogether, which no faster access link can do. It also reduces the load on the link (from 80 % to 52 %) and on the origin servers. Its limits: dynamic and personal pages cannot be cached, and HTTPS hides content from an institutional proxy unless the browser is configured to trust it.
Problem 3
A browser cache fetches /timetable.html at 10:00:00. The response contains Cache-Control: max-age=600 and ETag: "v1"; the body is 40 KB. The page changes on the server at 10:25:00, getting ETag: "v2". The user opens the page at 10:05, 10:12, 10:20 and 10:30. For each visit, say whether the browser contacts the server, what it sends, what it receives, and how many body bytes cross the network.
Show solution 10:05: the copy is fresh (age 300 s < 600 s). Served from the cache, no request, 0 bytes.
10:12: stale (age 720 s). Conditional GET with If-None-Match: "v1"; unchanged, so 304 Not Modified, 0 body bytes. The copy is fresh again until 10:22.
10:20: fresh (revalidated at 10:12). Served from the cache, no request.
10:30: stale. Conditional GET with If-None-Match: "v1"; the page has changed, so 200 OK with ETag: "v2" and the 40 KB body.
Total: 40 KB transferred once instead of four times, at the price of two small conditional requests. Note the risk: between 10:25 and 10:30 the user could have seen the old page. max-age trades freshness for speed. (See the freshness timeline in §3.1.)

C. One connection, many streams

Problem 4
A page needs a 1 MB video clip and 10 small icons of 10 KB each, all from one server, over a 10 Mbit/s bottleneck. The browser asks for the video first, then the icons. Ignore round trips and headers; 1 MB = 8 Mbit, 10 KB = 80 kbit.
  1. HTTP/1.1 on one persistent connection, without pipelining tricks: when does the first icon arrive? The last?
  2. HTTP/2 on one connection, the server interleaving the frames of all 11 streams in equal shares: when do the icons arrive? When does the video finish?
  3. In HTTP/2, a single TCP segment of the video is lost, and its retransmission takes 100 ms. Which streams are delayed? What would happen with HTTP/3?
Show solution 1. The video takes 8 / 10 = 0.8 s, then each icon 8 ms. First icon at 0.808 s, last at 0.88 s: head-of-line blocking.
2. Each of 11 streams gets 10/11 Mbit/s ≈ 0.91 Mbit/s. An icon (80 kbit) completes after about 88 ms, all ten together. The video then has the whole link and finishes at 0.88 s, as before. The total is the same, but the small objects no longer wait.
3. TCP delivers bytes in order, so every stream whose data follow the lost segment in the byte stream waits about 100 ms, the icons included. With HTTP/3 over QUIC each stream is delivered independently: only the video stream waits.

D. TLS: round trips, observers and certificates

Problem 5
A student on the café Wi-Fi opens https://mail.example.com/inbox?folder=work. The RTT to the server is 50 ms, and the DNS answer is already cached.
  1. How long until the first byte of the response with TCP + TLS 1.3? With TLS 1.2? With HTTP/3?
  2. List what the café's access point can see.
  3. Next morning the browser resumes the TLS session with 0-RTT data. Why do servers accept only safe, idempotent requests as 0-RTT data?
Show solution 1. TLS 1.3: TCP handshake (1 RTT) + TLS handshake (1 RTT) + request–response (1 RTT) = 150 ms. TLS 1.2: 200 ms. HTTP/3: 100 ms.
2. The access point can see:
  • the student's and the server's IP addresses, and the ports (443);

Problem 6
The server www.shop.ro sends a certificate for www.shop.ro, issued by an intermediate CA R11, whose certificate is issued by the root ISRG Root X1, present in the browser's trust store. For each case, does the browser accept the connection? Why?

  4. The leaf certificate expired yesterday.

E. TELNET, SSH host keys and tunnels

Problem 7
A capture of a TELNET session contains, from the server, the bytes FF FD 18 FF FD 20 FF FB 01 FF FB 03, and later, from the client, the characters s t u d e n t \r \n p a 5 5 w 0 r d \r \n.
  1. Decode the server's option bytes (0x18 = 24 is TERMINAL-TYPE, 0x20 = 32 is TERMINAL-SPEED).
  2. Why did the password not appear on the user's screen, although it appears in the capture?
  3. Give two other things an attacker on the path could do besides reading the password.
Show solution1. IAC DO TERMINAL-TYPE, IAC DO TERMINAL-SPEED (the server asks the client to report them), IAC WILL ECHO (the server will echo), IAC WILL SUPPRESS-GO-AHEAD.
2. After WILL ECHO the client stops echoing locally, and the server chooses not to echo during the password. Hiding characters on the screen does nothing on the wire: they travel in clear.
3. Any two of the following:
  • read everything else typed and displayed in the session;
  • inject commands into the TCP stream (session hijacking), since nothing authenticates the data;
  • reuse the password later, on other machines where the user chose the same one.
Problem 8
You have logged in to lab.cs.example.ro with SSH for months. Today ssh prints "WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!" and refuses to connect.
  1. Give two possible explanations.
  2. What should you do before connecting? What must you not do?
  3. Why does this warning protect you, even though no certification authority is involved?

Task 1: State and caching

web_server.py serves two things:

  • a page that counts your visits with a session cookie;
  • a file with an ETag and Cache-Control: max-age=30; POST /touch changes the file.

It prints the headers of every request it receives.

"""web_server.py - a small HTTP/1.1 server for Lab 4: cookies and caching.
usage: python3 web_server.py [port]    (listens on 127.0.0.1, default 8000)
  GET  /            a page that counts your visits with a session cookie
  GET  /notes.txt   a file with ETag, Last-Modified, Cache-Control max-age
  POST /touch       changes notes.txt, so that its ETag changes"""
import hashlib, secrets, sys, time
from email.utils import formatdate
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer

sessions = {}        # session id -> visits: the state lives on the server
notes = {"text": "Lecture 4 notes, version 1\n", "mtime": time.time()}


class Handler(BaseHTTPRequestHandler):
    protocol_version = "HTTP/1.1"               # persistent connections

    def send(self, code, body=b"", headers=()):
        self.send_response(code)
        for k, v in headers:
            self.send_header(k, v)
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        if body and self.command != "HEAD":
            self.wfile.write(body)

    def do_GET(self):
        print("   request headers:", dict(self.headers))
        if self.path == "/":
            cookies = {}
            for part in self.headers.get("Cookie", "").split(";"):
                if "=" in part:
                    k, v = part.strip().split("=", 1)
                    cookies[k] = v
            sid, extra = cookies.get("session"), []
            if sid not in sessions:     # first visit: new state, new key
                sid = secrets.token_hex(8)
                sessions[sid] = 0
                extra.append(("Set-Cookie", f"session={sid}; Path=/; "
                              "HttpOnly; SameSite=Lax"))
            sessions[sid] += 1
            body = (f"<p>Hello! This is visit number {sessions[sid]} "
                    f"of session {sid}.</p>\n").encode()
            self.send(200, body,
                      [("Content-Type", "text/html; charset=utf-8"), *extra])
        elif self.path == "/notes.txt":
            body = notes["text"].encode()
            etag = '"' + hashlib.sha1(body).hexdigest()[:12] + '"'
            if self.headers.get("If-None-Match") == etag:
                # conditional GET and the copy is still valid: no body
                self.send(304, headers=[("ETag", etag),
                                        ("Cache-Control", "max-age=30")])
                return
            modified = formatdate(notes["mtime"], usegmt=True)
            self.send(200, body, [("Content-Type", "text/plain"),
                                  ("ETag", etag),
                                  ("Last-Modified", modified),
                                  ("Cache-Control", "max-age=30")])
        else:
            self.send(404, b"not found\n", [("Content-Type", "text/plain")])

    do_HEAD = do_GET

    def do_POST(self):
        self.rfile.read(int(self.headers.get("Content-Length", 0)))
        if self.path == "/touch":

login_server.py imitates an old TELNET service: it asks for a login and a password and echoes lines. Before the password it sends the TELNET bytes IAC WILL ECHO, so that a TELNET client stops showing what you type.

"""login_server.py - a toy remote-login service that sends everything in
clear, like TELNET (Lab 4).
usage: python3 login_server.py [port]   (listens on 127.0.0.1, default 2323)
connect: telnet 127.0.0.1 2323   (nc 127.0.0.1 2323 shows the raw bytes)"""
import socket, sys, threading

IAC, WILL, WONT, DO, DONT = 255, 251, 252, 253, 254   # TELNET commands
ECHO = 1                                               # TELNET option 1


def read_line(conn):
    """Read one line, dropping TELNET negotiations (IAC command option)."""
    data = bytearray()
    while True:
        b = conn.recv(1)
        if not b:
            return None
        if b[0] == IAC:             # IAC DO/DONT/WILL/WONT option: skip it
            conn.recv(2)
            continue
        if b == b"\n":
            return data.decode(errors="replace").rstrip("\r")
        data += b


def session(conn, addr):
    with conn:
        conn.sendall(b"Toy login service (everything travels in clear)\r\n"
                     b"login: ")
        user = read_line(conn)
        # "I will echo": a TELNET client stops echoing what the user types
        conn.sendall(b"password: " + bytes([IAC, WILL, ECHO]))
        password = read_line(conn)
        conn.sendall(bytes([IAC, WONT, ECHO]) + b"\r\n")   # normal echo
        if user is None or password is None:
            return
        print(f"{addr[0]}:{addr[1]} logged in as {user!r}, "
              f"password {password!r}")
        conn.sendall(f"Welcome, {user}. Type a line, or 'quit'.\r\n".encode())
        while (line := read_line(conn)) not in (None, "quit"):
            conn.sendall(f"you said: {line}\r\n".encode())
        conn.sendall(b"bye\r\n")

Task 7: An FTP client of your own

The helpers of Laboratory 3 gain two functions. recv_line reads one CR LF-terminated line, as FTP replies need, and tcp_connect wraps getaddrinfo and connect.

/* Read one line ending in LF (CR LF is removed). Returns its length,
   0 if the peer closed before any byte, -1 on error or too long a line. */
static inline long recv_line(int fd, char *buf, size_t cap) {
    size_t n = 0;
    for (;;) {
        char ch;
        ssize_t r = recv(fd, &ch, 1, 0);
        if (r < 0) { if (errno == EINTR) continue; return -1; }
        if (r == 0) { if (n == 0) return 0; break; }
        if (ch == '\n') break;
        if (n + 1 >= cap) return -1;
        buf[n++] = ch;
    }
    if (n > 0 && buf[n - 1] == '\r') n--;
    buf[n] = '\0';
    return (long)n;
}

/* Connect a TCP socket to host:port, trying every address returned
   by getaddrinfo. */
static inline int tcp_connect(const char *host, const char *port) {
    struct addrinfo hints = {0}, *res, *ai;
    hints.ai_family = AF_UNSPEC;
    hints.ai_socktype = SOCK_STREAM;
    if (getaddrinfo(host, port, &hints, &res) != 0) return -1;
    int fd = -1;
    for (ai = res; ai; ai = ai->ai_next) {
        fd = socket(ai->ai_family, ai->ai_socktype, ai->ai_protocol);
        if (fd < 0) continue;
        if (connect(fd, ai->ai_addr, ai->ai_addrlen) == 0) break;
        close(fd); fd = -1;
    }
    freeaddrinfo(res);
    return fd;
}

The client works in six steps:

  1. it logs in;
  2. it chooses the transfer type;
  3. it asks for passive mode and decodes the 227 reply;
  4. it opens the data connection;
  5. it sends RETR or LIST;
  6. it copies everything it receives until the server closes the data connection: end of file in stream mode.
/* ftp_client.c - a minimal passive-mode FTP client (Computer Networks, Lab 4)
   usage: ./ftp_client host port user password ls [dir]
          ./ftp_client host port user password get file                  */
#include <stdio.h>
#include <stdlib.h>
#include <stdarg.h>
#include "netio.h"

static int ctrl;                              /* the control connection */

/* Read one reply, possibly multi-line ("150-..." ... "150 ..."),
   print it and return its three-digit code. */
static int reply(void) {
    char line[1024], first[4] = "";
    for (;;) {
        if (recv_line(ctrl, line, sizeof line) <= 0) {
            fprintf(stderr, "control connection lost\n");
            exit(1);
        }
        printf("<- %s\n", line);
        if (first[0] == '\0') memcpy(first, line, 3);  /* code of line 1 */
        if (strncmp(line, first, 3) == 0 && line[3] == ' ')
            return atoi(first);                        /* "ddd " ends it */
    }
}

/* Send one command terminated by CR LF (the password is not printed),
   then read and return the reply code. */
static int command(const char *fmt, ...) {
    char cmd[512];
    va_list ap;
    va_start(ap, fmt);
    vsnprintf(cmd, sizeof cmd - 2, fmt, ap);
    va_end(ap);
    printf("-> %s\n", strncmp(cmd, "PASS ", 5) == 0 ? "PASS ****" : cmd);
    strcat(cmd, "\r\n");
    if (send_all(ctrl, cmd, strlen(cmd)) < 0) { perror("send"); exit(1); }
    return reply();
}

int main(int argc, char *argv[]) {
    if (argc < 6) {
        fprintf(stderr, "usage: %s host port user password ls [dir]"
                        " | get file\n", argv[0]);
        return 1;
    }
    int get = strcmp(argv[5], "get") == 0;
    if ((ctrl = tcp_connect(argv[1], argv[2])) < 0) {
        fprintf(stderr, "cannot connect\n");
        return 1;
    }
    if (reply() != 220) return 1;                     /* service ready */
    if (command("USER %s", argv[3]) == 331 &&
        command("PASS %s", argv[4]) != 230) return 1;  /* logged in? */
    command(get ? "TYPE I" : "TYPE A");          /* image or ASCII type */

    /* PASV: the reply is 227 Entering Passive Mode (h1,h2,h3,h4,p1,p2) */
    printf("-> PASV\n");
    send_all(ctrl, "PASV\r\n", 6);
    char line[1024];
    int h1, h2, h3, h4, p1, p2;
    do {
        if (recv_line(ctrl, line, sizeof line) <= 0) return 1;
        printf("<- %s\n", line);
    } while (strncmp(line, "227 ", 4) != 0);
    char *q = strchr(line, '(');
    if (!q || sscanf(q, "(%d,%d,%d,%d,%d,%d)",
                     &h1, &h2, &h3, &h4, &p1, &p2) != 6) return 1;
    char port[8];
    snprintf(port, sizeof port, "%d", p1 * 256 + p2);
    printf("   data connection: %d.%d.%d.%d port %d*256+%d = %s\n",
           h1, h2, h3, h4, p1, p2, port);
    int data = tcp_connect(argv[1], port);   /* same host, port from PASV */
    if (data < 0) {
        fprintf(stderr, "cannot open data connection\n");
        return 1;
    }

    int code = get ? command("RETR %s", argv[6])
             : argc > 6 ? command("LIST %s", argv[6]) : command("LIST");
    if (code != 125 && code != 150) {            /* e.g. 550 no such file */
        close(data);
        command("QUIT");
        return 1;
    }
    FILE *out = get ? fopen(argv[6], "wb") : stdout;
    if (!out) { perror("fopen"); return 1; }
    char buf[4096];
    ssize_t n;
    long total = 0;
    while ((n = recv(data, buf, sizeof buf, 0)) > 0) {
        fwrite(buf, 1, (size_t)n, out);
        total += n;
    }
    close(data);              /* stream mode: end of file = connection closed */
    if (get) {
        fclose(out);
        printf("   %ld bytes written to %s\n", total, argv[6]);
    }
    reply();                                       /* 226 transfer complete */
    command("QUIT");                               /* 221 goodbye */
    close(ctrl);
    return 0;
}

Task 7: The FTP client with Winsock

netio_win.h adds recv_line and tcp_connect to the helpers of Laboratory 3, exactly as on Linux. The program differs from the Linux version only in the Winsock details you know: WSAStartup, SOCKET, closesocket, WSAGetLastError.

/* ftp_client_win.c - a minimal passive-mode FTP client with Winsock
   (Computer Networks, Lab 4)
   usage: ftp_client_win host port user password ls [dir]
          ftp_client_win host port user password get file               */
#include <stdio.h>
#include <stdlib.h>
#include <stdarg.h>
#include "netio_win.h"

static SOCKET ctrl;                           /* the control connection */

/* Read one reply, possibly multi-line ("150-..." ... "150 ..."),
   print it and return its three-digit code. */
static int reply(void) {
    char line[1024], first[4] = "";
    for (;;) {
        if (recv_line(ctrl, line, sizeof line) <= 0) {
            fprintf(stderr, "control connection lost\n");
            exit(1);
        }
        printf("<- %s\n", line);
        if (first[0] == '\0') memcpy(first, line, 3);  /* code of line 1 */
        if (strncmp(line, first, 3) == 0 && line[3] == ' ')
            return atoi(first);                        /* "ddd " ends it */
    }
}

/* Send one command terminated by CR LF (the password is not printed),
   then read and return the reply code. */
static int command(const char *fmt, ...) {
    char cmd[512];
    va_list ap;
    va_start(ap, fmt);
    vsnprintf(cmd, sizeof cmd - 2, fmt, ap);
    va_end(ap);
    printf("-> %s\n", strncmp(cmd, "PASS ", 5) == 0 ? "PASS ****" : cmd);
    strcat(cmd, "\r\n");
    if (send_all(ctrl, cmd, strlen(cmd)) < 0) {
        fprintf(stderr, "send failed: %d\n", WSAGetLastError());
        exit(1);
    }
    return reply();
}

int main(int argc, char *argv[]) {
    if (argc < 6) {
        fprintf(stderr, "usage: %s host port user password ls [dir]"
                        " | get file\n", argv[0]);
        return 1;
    }
    WSADATA wsa;
    if (WSAStartup(MAKEWORD(2, 2), &wsa) != 0) return 1;
    int get = strcmp(argv[5], "get") == 0;
    if ((ctrl = tcp_connect(argv[1], argv[2])) == INVALID_SOCKET) {
        fprintf(stderr, "cannot connect: %d\n", WSAGetLastError());
        return 1;
    }
    if (reply() != 220) return 1;                     /* service ready */
    if (command("USER %s", argv[3]) == 331 &&
        command("PASS %s", argv[4]) != 230) return 1;  /* logged in? */
    command(get ? "TYPE I" : "TYPE A");          /* image or ASCII type */

    /* PASV: the reply is 227 Entering Passive Mode (h1,h2,h3,h4,p1,p2) */
    printf("-> PASV\n");
    send_all(ctrl, "PASV\r\n", 6);
    char line[1024];
    int h1, h2, h3, h4, p1, p2;
    do {
        if (recv_line(ctrl, line, sizeof line) <= 0) return 1;
        printf("<- %s\n", line);
    } while (strncmp(line, "227 ", 4) != 0);
    char *q = strchr(line, '(');
    if (!q || sscanf(q, "(%d,%d,%d,%d,%d,%d)",
                     &h1, &h2, &h3, &h4, &p1, &p2) != 6) return 1;
    char port[8];
    snprintf(port, sizeof port, "%d", p1 * 256 + p2);
    printf("   data connection: %d.%d.%d.%d port %d*256+%d = %s\n",
           h1, h2, h3, h4, p1, p2, port);
    SOCKET data = tcp_connect(argv[1], port); /* same host, port from PASV */
    if (data == INVALID_SOCKET) {
        fprintf(stderr, "cannot open data connection\n");
        return 1;
    }

    int code = get ? command("RETR %s", argv[6])
             : argc > 6 ? command("LIST %s", argv[6]) : command("LIST");
    if (code != 125 && code != 150) {            /* e.g. 550 no such file */
        closesocket(data);
        command("QUIT");
        return 1;
    }
    FILE *out = get ? fopen(argv[6], "wb") : stdout;
    if (!out) { perror("fopen"); return 1; }
    char buf[4096];
    int n;
    long total = 0;
    while ((n = recv(data, buf, sizeof buf, 0)) > 0) {
        fwrite(buf, 1, (size_t)n, out);
        total += n;
    }
    closesocket(data);        /* stream mode: end of file = connection closed */
    if (get) {
        fclose(out);
        printf("   %ld bytes written to %s\n", total, argv[6]);
    }
    reply();                                       /* 226 transfer complete */
    command("QUIT");                               /* 221 goodbye */
    closesocket(ctrl);
    WSACleanup();
    return 0;
}

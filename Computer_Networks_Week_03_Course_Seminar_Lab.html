1. From the bottom of the stack to the top

In the first two weeks we looked at the Internet as a whole: its parts, its layers and its performance. From today we go down the stack one layer at a time, starting from the top: the application layer. Its protocols are the ones you use every day, and it is the layer most of you will program for the rest of your careers. Two things happen this week. In the lecture we study how network applications are organised, and the protocol of the Web, HTTP. In the laboratory you write your first network programs, a TCP client and a TCP server, using the same interface every browser and web server uses.

2. Application architectures

A network application is a set of programs running on different end systems and communicating over the network. Its designer first chooses an architecture: how the roles are divided between the programs. Routers and switches are not involved. They do not run application code, which is why new applications can be deployed without changing the network.

Many real systems are hybrids: a messaging service uses servers to find users and relay offline messages, while a voice or video call may flow directly between the two phones.

3. Processes, addresses and sockets

Hosts do not communicate; processes do: programs running on hosts.

  • Two processes on the same host communicate through the operating system (pipes, shared memory).
  • Processes on different hosts communicate by exchanging messages across the network.
  • In each exchange, the process that starts it is the client and the one waiting to be contacted is the server. In a P2P file transfer, the same peer is the client in one exchange and the server in another.

3.1 The socket: a door between the application and transport

A process sends and receives messages through a software interface called a socket. A good picture is a door: the process pushes a message out of its door and relies on the transport infrastructure on the other side to deliver it to the door of the destination process. The application developer controls everything on the application side of the socket. On the transport side, the only choices are the transport protocol and a few parameters (buffer sizes, timeouts). 3.2 Addressing a process

To send a message to a process on another host, a sender needs two things:

  • the IP address of the host (32 bits in IPv4, 128 bits in IPv6), which identifies the host's network interface; and
  • a port number (16 bits), which identifies the receiving process, or strictly the receiving socket, on that host.

Well-known services use well-known ports: HTTP 80, HTTPS 443, DNS 53, SMTP 25, SSH 22. A client's operating system gives its socket a temporary ephemeral port. A TCP connection is identified by four numbers together, the 4-tuple (source IP, source port, destination IP, destination port). This is how a web server with thousands of open connections to port 443 tells them apart: no two have the same 4-tuple.

4. What applications need from transport

When you create a socket you choose a transport protocol. The right choice depends on what the application needs, along four dimensions:

  • Reliable data transfer. Must every byte arrive, intact and in order? A file transfer or a bank transaction tolerates no loss. A video call tolerates some: a lost fragment of a frame is better than a late one.
  • Throughput. Does the application need a minimum rate (a video stream at 5 Mbit/s), or can it use whatever is available (e-mail and file transfer, which are elastic applications)?
  • Timing. Must data arrive within some delay? Interactive games and voice need tens of milliseconds; a file download does not care.
  • Security. Confidentiality, integrity and authentication of the endpoints.

Neither protocol guarantees timing or throughput: the Internet is best effort, as we saw in Lecture 1. Applications that need them cope through design: buffering, adapting their rate, choosing nearby servers.

Neither protocol encrypts either. Security is added above transport by TLS (Transport Layer Security), a library that the application calls instead of the plain socket, giving an encrypted, authenticated TCP connection; HTTPS is HTTP over TLS. QUIC, the transport under HTTP/3, runs over UDP and builds reliability, congestion control and TLS encryption into one protocol.

Why would anyone choose UDP?Because sometimes the services of TCP get in the way:
  • TCP's retransmissions and ordering can hold back fresh data behind old lost data.
  • Its handshake costs a round trip before the first byte.
  • Its congestion control may slow down a sender that would rather lose some data than arrive late.
An application on UDP can add exactly the reliability it needs, or build a whole new transport, as QUIC does.

5. What an application-layer protocol defines

An application-layer protocol fixes, for the processes of one application:

  • the types of messages exchanged, for example requests and responses;
  • the syntax of each type: its fields and how they are delimited;
  • the semantics of the fields: what the information in them means;
  • the rules for when and how a process sends messages and responds to them.

Some protocols are open, specified in public RFCs so that anyone can write a compatible program: HTTP, SMTP, DNS. Others are proprietary, such as many messaging and video-call protocols. Note the distinction between an application and its application-layer protocol. The Web is an application made of HTML documents, browsers, web servers and standards; HTTP is only the protocol by which browsers and servers exchange messages.

6. The Web: objects and URLs

A web page consists of objects: files such as an HTML document, images, style sheets, scripts and videos, each addressable by a URL (Uniform Resource Locator). Most pages are a base HTML file that references many other objects; a typical news page today references well over a hundred.

  • The host is resolved by DNS to an IP address.
  • The port is optional and defaults to 80 for http and 443 for https.
  • The path names the object on the server, and the query passes parameters.
  • The fragment is used only by the browser, to scroll to a part of the page. It is never sent to the server.

HTTP (HyperText Transfer Protocol) is the Web's application-layer protocol. The client (browser) sends a request for an object, and the server returns a response containing it. HTTP/1.1 and HTTP/2 run over TCP; HTTP/3 runs over QUIC.

HTTP is stateless: the server keeps no memory of earlier requests from the same client. Statelessness makes servers simpler and more robust. When an application needs state (a login, a shopping basket), it is added on top with cookies, which we study next week.

7. HTTP connections and their cost in round trips

How many TCP connections should a browser use to fetch a page and its objects? There are two basic answers, and the difference is measured in round-trip times (RTT): the time for a small packet to go from client to server and back.

7.1 Non-persistent connections

There is one TCP connection per object: open the connection, send the request, receive the response, close. Each object costs one RTT to set up TCP (the client sends SYN and waits for SYN-ACK), plus one RTT for the request and the start of the response, plus the time to transmit the object:

time per object = 2 RTT + transmission time

HTTP/1.0 worked this way. Besides the extra round trips, every connection costs the server memory, and the start of every connection runs slowly while TCP probes the available rate (we see why in the transport lectures).

7.2 Persistent connections

The server leaves the TCP connection open after responding, and later requests between the same client and server reuse it. After the first object, each further object costs one RTT plus its transmission time. Persistent connections are the default in HTTP/1.1. The connection is closed when either side sends Connection: close, or after a period of inactivity.

7.3 Doing several things at once

  • Parallel connections. Browsers open several TCP connections to the same server at once (typically up to six for HTTP/1.1), fetching several objects simultaneously. This hides latency but multiplies the server load and competes unfairly with other users' single connections.
  • Pipelining. HTTP/1.1 allows a client to send several requests on one connection without waiting for the responses. Responses must come back in order, so one slow response blocks those behind it: head-of-line blocking. Browsers disabled pipelining in practice.
  • Multiplexing. HTTP/2 splits requests and responses into frames and interleaves them on one TCP connection, removing head-of-line blocking at the HTTP level. HTTP/3 also removes it at the transport level, by running over QUIC. Both come next week.
Worked example

A page has a base HTML file and 10 small images on the same server. RTT = 50 ms; ignore transmission and DNS.

  • Non-persistent, one at a time: 11 objects × 2 RTT = 22 RTT = 1100 ms.
  • Non-persistent, 5 parallel connections for the images: base 2 RTT, then two rounds of images × 2 RTT = 6 RTT = 300 ms.
  • Persistent, one request at a time: 2 RTT for the base page (including the handshake) + 10 × 1 RTT = 12 RTT = 600 ms.
  • Persistent with pipelining (or HTTP/2): 2 RTT for the base page + 1 RTT for all images = 3 RTT = 150 ms.

The round trip, not the link rate, dominates the loading of pages made of many small objects.

8. HTTP/1.1 messages

HTTP/1.1 messages are text: lines of ASCII characters, each ending in carriage return and line feed (CR LF, written \r\n). That is why you could type a request by hand in Laboratory 1. The current specifications are RFC 9110 (HTTP semantics, common to all versions) and RFC 9112 (the HTTP/1.1 message format), both from 2022.

A request has four parts:

  • The request line gives the method, the target (the path and query of the URL) and the version.
  • Header lines follow, one per line. The Host header is mandatory in HTTP/1.1: one server, with one IP address, may host thousands of sites, and the Host header tells it which one is meant.
  • An empty line ends the header.
  • Some requests then carry a body, for example the data of a submitted form.

8.3 Where does a message end?

TCP delivers a stream of bytes with no boundaries between messages (§9). A receiver therefore needs a rule to know where each HTTP message ends; otherwise, on a persistent connection, it cannot tell the end of one response from the start of the next. HTTP/1.1 uses three rules:

  1. The header ends at the first empty line. The receiver reads lines until it finds \r\n\r\n.
  2. A body of known length is announced with Content-Length: the receiver reads exactly that many bytes after the header.
  3. A body of unknown length (generated while it is being sent) uses Transfer-Encoding: chunked. The body is sent as chunks, each preceded by its length in hexadecimal on a line of its own, and ended by a chunk of length 0. (A server may also simply close the connection at the end of the body, but then the connection cannot be reused.)

9. The socket API, step by step

The Berkeley sockets interface appeared in 4.2BSD UNIX in 1983 and is today the interface of every operating system. Windows implements it as Winsock, with small differences that the Windows laboratory sheet lists. Figure 2 shows the calls made by a TCP server and a TCP client.

CallWhoWhat it does
socket()bothCreates a socket: address family (IPv4/IPv6) and type (stream = TCP, datagram = UDP). Returns a descriptor.
bind()serverAttaches the socket to a local address and port, such as 0.0.0.0:8080.
listen()serverMarks the socket as passive: it will accept connections. Sets the length of the queue of pending connections.
connect()clientStarts the TCP handshake with the server's address and port. The OS picks an ephemeral local port.

9.1 Three facts that surprise beginners

  • A stream has no message boundaries. Two send() calls of 5 bytes may arrive as one recv() of 10 bytes, or as recv() calls of 3 and 7. One send() of 300 000 bytes may arrive in five pieces of different sizes. A program must loop until it has the bytes it expects, and the protocol must define where a message ends.
  • send() may accept fewer bytes than asked. It returns the number of bytes copied into the operating system's buffer, and the rest must be sent again. A correct program wraps it in a loop (send_all in the laboratory; sendall in Python).
  • Byte order matters. Port numbers, addresses and any binary integers sent over the network use network byte order (big-endian). The functions htons, htonl, ntohs and ntohl convert between host and network order. Forgetting them is the classic bug that makes a server listen on port 36895 instead of 8080 on an x86 machine.

10. Summary and key terms

  • Network applications run only on end systems, organised as client–server, peer-to-peer or a hybrid.
  • Processes communicate through sockets. A process is addressed by IP address + port, and a TCP connection is identified by its 4-tuple.
  • Applications differ in their needs for reliability, throughput, timing and security.
    • TCP gives a reliable, ordered byte stream with flow and congestion control.
    • UDP gives bare datagrams.
    • TLS adds security; neither transport gives timing guarantees.
  • An application-layer protocol defines message types, syntax, semantics and rules.
  • The Web is made of objects named by URLs and fetched with HTTP, a stateless request–response protocol.
  • Non-persistent HTTP costs 2 RTT per object; persistent HTTP costs 1 RTT per object after the first. Parallel connections, pipelining and multiplexing reduce page-load times further.
  • HTTP/1.1 messages are text: a request or status line, headers, an empty line, an optional body. The body's end is given by Content-Length or chunked encoding: the framing problem every TCP protocol must solve.
  • TCP servers call socket, bind, listen, accept; clients call socket, connect; both call send, recv, close.

11. Review questions and exercises

The source gives answers for the exercises. For the review questions a short model answer has been added; try to answer before opening it.

R1. Why can a new network application be deployed without any change to the Internet's routers?
Model answerApplication code runs only on end systems. Routers forward packets using network-layer information and never look at application messages, so a new application needs only programs on the hosts that use it.
R2. In a BitTorrent download, which peer is the client and which the server? Can the answer change during the download?
Model answerIn each exchange, the peer that requests a piece is the client and the peer that sends it is the server. Every peer does both, often at the same time with different neighbours, so the roles change constantly.
R3. A web server has 10 000 open TCP connections, all to its port 443. How does it deliver an arriving segment to the right connection?
Model answerBy the full 4-tuple (source IP, source port, destination IP, destination port). The destination part is the same for all of them, but no two connections share the client's IP and port.
R4. Give one application for which UDP is a better choice than TCP, and explain which TCP service would get in its way.
Model answerA video call or a racing game. TCP's in-order reliable delivery would hold back fresh data behind retransmissions of old, already useless data, and congestion control could slow the sender instead of letting it drop a little quality.
R5. Neither TCP nor UDP encrypts. How does HTTPS protect a connection, and at which layer?
Model answerHTTPS is HTTP over TLS. The application writes into a TLS library, which encrypts, authenticates and integrity-protects the data before handing it to TCP. Protection is added above transport, inside the application.
R6. Which part of a URL is never sent to the server? Why?
Model answerThe fragment (after #). It names a place inside the received document, which only the browser uses, for example to scroll there.
R7. Why is the Host header mandatory in HTTP/1.1?
Model answerOne server with one IP address may host many sites (virtual hosting). The request line carries only the path, so the Host header tells the server which site is meant.
R8. Explain why a browser may safely repeat a GET request but should warn before repeating a POST.
Model answerGET is safe and idempotent: repeating it changes nothing. POST is neither: the first request may already have placed an order or sent a message, and repeating it could do so twice.
R9. Give two ways in which an HTTP/1.1 receiver can know where a response body ends.
Model answerContent-Length (read exactly that many bytes), or Transfer-Encoding: chunked (read chunks until a chunk of size 0). A third, legacy way: the server closes the connection.
R10. What does accept() return, and why is it not the listening socket itself?
Model answerA new descriptor for a connected socket, bound to one specific client (one 4-tuple). The listening socket must stay open to accept further clients, and it never carries data.

5. Here transmission (240 ms for the images) and RTTs (40 ms each) are comparable. With 60 small images, each takes 0.8 ms to transmit. With many small objects the round trips dominate. (Try it in the page-load calculator.)

Problem 10: design
You must design the protocol of a small file-upload service over TCP. The client sends a file name and the file's bytes; the server answers OK or an error. The file may contain any bytes, including newlines and zeros. Specify the exact message format, so that two students could implement the client and the server independently.
One possible answer
  • Request: a header line in text, then the raw bytes: PUT <name> <size>\r\n followed by exactly <size> bytes. The name may not contain spaces or CR LF; the size is decimal.
  • Response: one line: OK\r\n, or ERR <code> <text>\r\n (for example ERR 413 too large).

All programs share the helpers in netio.h. send_all and recv_all loop until all the requested bytes are written or read; send_msg and recv_msg are used in Task 7.

/* netio.h - helpers for TCP byte streams (Computer Networks, Lab 3) */
#ifndef NETIO_H
#define NETIO_H
#include <stdint.h>
#include <errno.h>
#include <unistd.h>
#include <arpa/inet.h>
#include <sys/socket.h>

/* Write exactly len bytes. Returns 0 on success, -1 on error. */
static inline int send_all(int fd, const void *buf, size_t len) {
    const char *p = buf;
    while (len > 0) {
        ssize_t n = send(fd, p, len, 0);
        if (n < 0) { if (errno == EINTR) continue; return -1; }
        p += n; len -= (size_t)n;
    }
    return 0;
}

/* Read exactly len bytes. Returns 1 on success, 0 if the peer closed first, -1 on error. */
static inline int recv_all(int fd, void *buf, size_t len) {
    char *p = buf;
    while (len > 0) {
        ssize_t n = recv(fd, p, len, 0);
        if (n < 0) { if (errno == EINTR) continue; return -1; }
        if (n == 0) return 0;
        p += n; len -= (size_t)n;
    }
    return 1;
}

/* Length-prefixed messages: 4-byte length in network byte order, then the payload. */
static inline int send_msg(int fd, const void *buf, uint32_t len) {
    uint32_t netlen = htonl(len);
    if (send_all(fd, &netlen, sizeof netlen) < 0) return -1;
    return send_all(fd, buf, len);
}

/* Returns the payload length, 0 if the peer closed, -1 on error or if the message exceeds cap. */
static inline long recv_msg(int fd, void *buf, uint32_t cap) {
    uint32_t netlen;
    int r = recv_all(fd, &netlen, sizeof netlen);
    if (r <= 0) return r;
    uint32_t len = ntohl(netlen);
    if (len > cap) return -1;
    r = recv_all(fd, buf, len);
    return r <= 0 ? -1 : (long)len;
}
#endif

The client resolves the server's name with getaddrinfo, tries each address it gets (IPv6 and IPv4) until connect succeeds, then sends each line it reads from the keyboard and prints the echo:

/* echo_client.c - send each line of standard input to a TCP server, print what comes back.
   Usage: ./echo_client HOST PORT */
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <netdb.h>
#include <sys/socket.h>
#include "netio.h"

int main(int argc, char *argv[]) {
    if (argc != 3) { fprintf(stderr, "usage: %s HOST PORT\n", argv[0]); return 1; }

    struct addrinfo hints = {0}, *res, *ai;
    hints.ai_family = AF_UNSPEC;          /* IPv4 or IPv6 */
    hints.ai_socktype = SOCK_STREAM;      /* TCP */
    int err = getaddrinfo(argv[1], argv[2], &hints, &res);
    if (err) { fprintf(stderr, "getaddrinfo: %s\n", gai_strerror(err)); return 1; }

    int fd = -1;
    for (ai = res; ai != NULL; ai = ai->ai_next) {          /* try each address in turn */
        fd = socket(ai->ai_family, ai->ai_socktype, ai->ai_protocol);
        if (fd < 0) continue;
        if (connect(fd, ai->ai_addr, ai->ai_addrlen) == 0) break;
        close(fd); fd = -1;
    }
    freeaddrinfo(res);
    if (fd < 0) { perror("connect"); return 1; }

    char line[1024], reply[1024];
    while (fgets(line, sizeof line, stdin) != NULL) {
        size_t len = strlen(line);
        if (send_all(fd, line, len) < 0) { perror("send"); break; }
        /* The echo has the same length as what we sent, but may arrive in pieces. */
        int r = recv_all(fd, reply, len);
        if (r <= 0) { fprintf(stderr, r == 0 ? "server closed the connection\n" : "recv failed\n"); break; }
        fwrite(reply, 1, len, stdout);
    }
    close(fd);
    return 0;
}

/* echo_server.c - iterative TCP echo server: one client at a time.
   Usage: ./echo_server PORT */
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <arpa/inet.h>
#include <netinet/in.h>
#include <sys/socket.h>
#include "netio.h"

int main(int argc, char *argv[]) {
    if (argc != 2) { fprintf(stderr, "usage: %s PORT\n", argv[0]); return 1; }

    setvbuf(stdout, NULL, _IOLBF, 0);                         /* print each line at once */
    int lfd = socket(AF_INET, SOCK_STREAM, 0);               /* 1. create */
    if (lfd < 0) { perror("socket"); return 1; }
    int on = 1;
    setsockopt(lfd, SOL_SOCKET, SO_REUSEADDR, &on, sizeof on); /* allow quick restarts */

    struct sockaddr_in addr = {0};
    addr.sin_family = AF_INET;
    addr.sin_addr.s_addr = htonl(INADDR_ANY);                 /* all local addresses */
    addr.sin_port = htons((uint16_t)atoi(argv[1]));            /* host -> network byte order */
    if (bind(lfd, (struct sockaddr *)&addr, sizeof addr) < 0) { perror("bind"); return 1; } /* 2. bind */
    if (listen(lfd, 8) < 0) { perror("listen"); return 1; }  /* 3. listen, backlog 8 */
    printf("listening on port %s\n", argv[1]);

    for (;;) {
        struct sockaddr_in peer; socklen_t plen = sizeof peer;
        int cfd = accept(lfd, (struct sockaddr *)&peer, &plen); /* 4. accept: a NEW socket */
        if (cfd < 0) { perror("accept"); continue; }
        char ip[INET_ADDRSTRLEN];
        inet_ntop(AF_INET, &peer.sin_addr, ip, sizeof ip);
        printf("connection from %s:%u\n", ip, ntohs(peer.sin_port));

        char buf[65536]; ssize_t n; long total = 0;
        while ((n = recv(cfd, buf, sizeof buf, 0)) > 0) {      /* 5. read what has arrived */
            printf("  recv returned %zd bytes\n", n);
            total += n;
            if (send_all(cfd, buf, (size_t)n) < 0) { perror("send"); break; }
        }
        printf("client closed after %ld bytes\n", total);
        close(cfd);                                            /* 6. close this connection */
    }
}

upper_server implements a line-based protocol: for each line ending in \n it replies with the line in upper case. Its loop keeps a buffer, because one recv may contain half a line, a whole line or several lines:

    for (;;) {
        int cfd = accept(lfd, NULL, NULL);
        if (cfd < 0) continue;
        char buf[4096]; size_t used = 0; ssize_t n;
        while ((n = recv(cfd, buf + used, sizeof buf - used, 0)) > 0) {
            used += (size_t)n;
            char *nl;
            /* A single recv may hold part of a line, one line, or several lines. */
            while ((nl = memchr(buf, '\n', used)) != NULL) {
                size_t linelen = (size_t)(nl - buf) + 1;
                for (size_t i = 0; i < linelen; i++) buf[i] = (char)toupper((unsigned char)buf[i]);
                if (send_all(cfd, buf, linelen) < 0) break;
                memmove(buf, buf + linelen, used - linelen);   /* keep the rest for later */
                used -= linelen;
            }
            if (used == sizeof buf) { const char *e = "ERR line too long\n"; send_all(cfd, e, strlen(e)); break; }
        }
        close(cfd);

Task 2: The echo client

The helpers are the same as on Linux, with Winsock types:

/* netio_win.h - helpers for TCP byte streams on Windows (Winsock 2) - Computer Networks, Lab 3 */
#ifndef NETIO_WIN_H
#define NETIO_WIN_H
#include <winsock2.h>
#include <ws2tcpip.h>
#include <stdint.h>

/* Write exactly len bytes. Returns 0 on success, -1 on error. */
static inline int send_all(SOCKET s, const void *buf, size_t len) {
    const char *p = buf;
    while (len > 0) {
        int n = send(s, p, (int)len, 0);
        if (n == SOCKET_ERROR) return -1;
        p += n; len -= (size_t)n;
    }
    return 0;
}

/* Read exactly len bytes. Returns 1 on success, 0 if the peer closed first, -1 on error. */
static inline int recv_all(SOCKET s, void *buf, size_t len) {
    char *p = buf;
    while (len > 0) {
        int n = recv(s, p, (int)len, 0);
        if (n == SOCKET_ERROR) return -1;
        if (n == 0) return 0;
        p += n; len -= (size_t)n;
    }
    return 1;
}

static inline int send_msg(SOCKET s, const void *buf, uint32_t len) {
    uint32_t netlen = htonl(len);
    if (send_all(s, &netlen, sizeof netlen) < 0) return -1;
    return send_all(s, buf, len);
}

static inline long recv_msg(SOCKET s, void *buf, uint32_t cap) {
    uint32_t netlen;
    int r = recv_all(s, &netlen, sizeof netlen);
    if (r <= 0) return r;
    uint32_t len = ntohl(netlen);
    if (len > cap) return -1;
    r = recv_all(s, buf, len);
    return r <= 0 ? -1 : (long)len;
}

/* echo_client_win.c - Winsock version of echo_client.c.
   Build:  gcc echo_client_win.c -o echo_client.exe -lws2_32     (MinGW-w64)
      or:  cl echo_client_win.c ws2_32.lib                         (Visual Studio)
   Usage:  echo_client.exe HOST PORT */
#include <stdio.h>
#include <string.h>
#include "netio_win.h"
#ifdef _MSC_VER
#pragma comment(lib, "ws2_32.lib")
#endif

int main(int argc, char *argv[]) {
    if (argc != 3) { fprintf(stderr, "usage: %s HOST PORT\n", argv[0]); return 1; }
    WSADATA wsa;
    if (WSAStartup(MAKEWORD(2, 2), &wsa) != 0) { fprintf(stderr, "WSAStartup failed\n"); return 1; }

    struct addrinfo hints = {0}, *res, *ai;
    hints.ai_family = AF_UNSPEC; hints.ai_socktype = SOCK_STREAM;
    int err = getaddrinfo(argv[1], argv[2], &hints, &res);
    if (err) { fprintf(stderr, "getaddrinfo failed: %d\n", err); WSACleanup(); return 1; }

    SOCKET s = INVALID_SOCKET;
    for (ai = res; ai != NULL; ai = ai->ai_next) {
        s = socket(ai->ai_family, ai->ai_socktype, ai->ai_protocol);
        if (s == INVALID_SOCKET) continue;
        if (connect(s, ai->ai_addr, (int)ai->ai_addrlen) == 0) break;
        closesocket(s); s = INVALID_SOCKET;
    }
    freeaddrinfo(res);
    if (s == INVALID_SOCKET) { fprintf(stderr, "connect failed: error %d\n", WSAGetLastError()); WSACleanup(); return 1; }

    char line[1024], reply[1024];
    while (fgets(line, sizeof line, stdin) != NULL) {
        size_t len = strlen(line);
        if (send_all(s, line, len) < 0) { fprintf(stderr, "send failed: %d\n", WSAGetLastError()); break; }
        int r = recv_all(s, reply, len);
        if (r <= 0) { fprintf(stderr, r == 0 ? "server closed the connection\n" : "recv failed\n"); break; }
        fwrite(reply, 1, len, stdout);
    }
    closesocket(s);
    WSACleanup();
    return 0;
}

Task 3: The echo server

/* echo_server_win.c - Winsock version of echo_server.c (iterative, one client at a time).
   Build:  gcc echo_server_win.c -o echo_server.exe -lws2_32
   Usage:  echo_server.exe PORT */
#include <stdio.h>
#include <stdlib.h>
#include "netio_win.h"
#ifdef _MSC_VER
#pragma comment(lib, "ws2_32.lib")
#endif

int main(int argc, char *argv[]) {
    if (argc != 2) { fprintf(stderr, "usage: %s PORT\n", argv[0]); return 1; }
    setvbuf(stdout, NULL, _IONBF, 0);
    WSADATA wsa;
    if (WSAStartup(MAKEWORD(2, 2), &wsa) != 0) { fprintf(stderr, "WSAStartup failed\n"); return 1; }

    SOCKET ls = socket(AF_INET, SOCK_STREAM, IPPROTO_TCP);
    if (ls == INVALID_SOCKET) { fprintf(stderr, "socket: %d\n", WSAGetLastError()); return 1; }

    struct sockaddr_in addr = {0};
    addr.sin_family = AF_INET;
    /* Loopback only: avoids the Windows Firewall prompt. Use INADDR_ANY to accept other machines. */
    addr.sin_addr.s_addr = htonl(INADDR_LOOPBACK);
    addr.sin_port = htons((u_short)atoi(argv[1]));
    if (bind(ls, (struct sockaddr *)&addr, sizeof addr) == SOCKET_ERROR) { fprintf(stderr, "bind: %d\n", WSAGetLastError()); return 1; }
    if (listen(ls, 8) == SOCKET_ERROR) { fprintf(stderr, "listen: %d\n", WSAGetLastError()); return 1; }
    printf("listening on 127.0.0.1:%s\n", argv[1]);

    for (;;) {
        struct sockaddr_in peer; int plen = sizeof peer;
        SOCKET cs = accept(ls, (struct sockaddr *)&peer, &plen);
        if (cs == INVALID_SOCKET) { fprintf(stderr, "accept: %d\n", WSAGetLastError()); continue; }
        char ip[INET_ADDRSTRLEN];
        inet_ntop(AF_INET, &peer.sin_addr, ip, sizeof ip);
        printf("connection from %s:%u\n", ip, ntohs(peer.sin_port));

        char buf[65536]; int n; long total = 0;
        while ((n = recv(cs, buf, sizeof buf, 0)) > 0) {
            printf("  recv returned %d bytes\n", n);
            total += n;
            if (send_all(cs, buf, (size_t)n) < 0) break;
        }
        printf("client closed after %ld bytes\n", total);
        closesocket(cs);
    }
}

The same programs in Python

The files in python/ run unchanged on Windows: python python\echo_server.py 5000 and python python\echo_client.py 127.0.0.1 5000. Python hides WSAStartup and the type differences, but the stream behaviour, and the need for recv_all, is exactly the same.

"""echo_client.py - send lines from standard input, print the echo. Usage: python echo_client.py HOST PORT"""
import socket, sys

def recv_all(sock, n):
    """Read exactly n bytes, or raise if the peer closes first."""
    chunks = []
    while n > 0:
        data = sock.recv(n)
        if not data:
            raise ConnectionError("server closed the connection")
        chunks.append(data)
        n -= len(data)
    return b"".join(chunks)

with socket.create_connection((sys.argv[1], int(sys.argv[2]))) as s:
    for line in sys.stdin:
        data = line.encode()
        s.sendall(data)
        print(recv_all(s, len(data)).decode(), end="")
